## Next up
- **Quotes F3 is now fully complete** (Stage 3 landed 2026-08-07 — see Completed below). The only two F3 stories not yet built are **S-03.10 (quote → job/invoice conversion)** and **S-03.12 (mobile)** — both explicitly out of scope until Jobs/Invoices/`apps/mobile` exist, per the PRD's own phase breakdown (`docs/spine-prd.md` §12). - Stage 3's own known gaps/rough edges, left as-is because nothing in the task brief called for going further:
  - **Repeat-view notifications aren't de-duplicated.** Every successful public view writes a `quote_events` row AND fires an owner-notification email (S-03.7's literal wording — "the moment a quote is viewed" — doesn't say "only the first time"), so a customer who opens the link five times generates five "viewed" emails. This is very likely to feel noisy in real use; a reasonable follow-up is throttling to "at most one 'viewed' notification per hour per quote" or similar, deliberately not built here since the PRD text doesn't call for it and doing so would be inventing scope.
  - **A rejection does not trigger an owner notification** — only "viewed" and "accepted" do, matching S-03.7's own wording exactly ("viewed or accepted"). The quote's status flip to `rejected` is visible on the authenticated detail page, but there's no proactive email for it. Worth reconsidering if real usage shows owners want to know about rejections just as promptly.
  - **Rate limiting (20 req/min/IP, `@nestjs/throttler`, in-memory) is a first pass, not tuned against real traffic.** It's per-IP only — a customer and their whole office behind one NAT'd IP share the same bucket, which could be too tight for legitimate shared use (e.g. several people at a company opening the same link) or too loose against a determined attacker rotating source IPs. In-memory (no Redis, per CLAUDE.md's single-host stance) also means the limit resets on every API process restart, which is a fine tradeoff for a single-host deployment but wouldn't survive a future multi-instance one without swapping storage.
  - **Token TTL is a flat 30 days**, not configurable per-org or tied to the quote's own `validUntil`. A quote valid for only 7 days still gets a 30-day link — not incorrect (the public page/accept/reject flow independently checks `status === "sent"`, so an expired-by-`validUntil` quote can still technically be viewed/accepted via a live token, matching how the authenticated app treats "expired" as informational, not a hard block — see `QuotesService`'s own `isExpired` comment), but worth a second look if the PRD's "expire" semantics are meant to be a hard cutoff on the public side too.
  - **No public "resend my link" self-service** — if a customer loses the email, only staff re-sending (or revising) the quote mints a fresh token. This wasn't asked for and would need its own rate-limiting/abuse consideration (an anonymous "resend to this email" endpoint is a classic enumeration/spam vector) so it's deliberately not built.
  - **The public web page's actual rendered UI was not visually verified** — no browser-automation tooling exists in this environment (same limitation noted in every prior Quotes session). What *was* verified live: the underlying `GET/POST /public/quotes/:token` calls the page's client component makes (directly, with curl, using a token minted the same way the real send flow mints one), that the Next.js route resolves and server-renders without error, and that `pnpm --filter @spine/web build` successfully compiles `/quote/[token]` as a route. The actual on-screen layout, mobile responsiveness, and dark/light theming were reviewed by reading the component's Tailwind classes against `@spine/ui`'s existing conventions, not by looking at a rendered browser.

### 2026-08-08 — S-12.9: wire the dashboard setup checklist to real completion state

- User asked "what's next" after the production Docker fix; picked S-12.9 (the dashboard's "first customer / first item / first quote" checklist, previously a static always-unchecked placeholder from before Contacts/Catalogue/Quotes existed) as the last small gap in Phase 1's own story list.
- New `DashboardModule`/`DashboardService`/`DashboardController` (`apps/api/src/modules/dashboard/`) — `GET /dashboard/checklist` returns `{hasCustomer, hasItem, hasSentQuote, dismissed}` in one call: three parallel existence checks (`isDemo: false` + not-archived/not-draft, so demo-seeded data and unsent draft quotes don't count) plus the persisted dismissed flag, all from the `settings` table's `dashboard_checklist_dismissed` key.
- **Review pass caught a real authz bug before this shipped**: the original version wrote dismissal through the existing `PUT /org/settings/:key`, which is `@OrgRoles(["owner"])`-only by design (real org config shouldn't be staff-writable) — but the checklist itself is shown to and dismissible by every org member, so any staff/field user hit a silent 403 on dismiss (and on the new auto-dismiss-when-complete behavior), making the checklist reappear on every visit forever for anyone but the owner. Fixed with a dedicated `POST /dashboard/checklist/dismiss` (no `@OrgRoles` restriction, matching the read side) that writes straight to the same `settings` row rather than loosening the owner-only gate for every other setting.
- Review also caught a stuck-spinner regression in the first draft: the fetch-error `.catch` set a "not dismissed" flag but never populated `status`, so a failed `/dashboard/checklist` call left the card permanently showing its loading spinner instead of degrading. Fixed by collapsing to one endpoint/one error state — a failed fetch now hides the card entirely rather than getting stuck.
- Six parallel review passes (different angles: line-by-line diff, cross-file authz tracing, reuse/duplication, simplification/efficiency, altitude/conventions, removed-behavior) were run against this change; the authz bug and stuck-spinner bug were independently rediscovered by multiple passes, which is what confirmed they were real rather than false positives. Also fixed on the review's recommendation: the auto-dismiss-on-completion write is now guarded by a ref so a component remount doesn't refire it while a prior write is in flight, and its failure is logged instead of silently swallowed.
- Two findings were deliberately left as-is: (1) auto-dismiss is a one-way ratchet — if an org later archives its only contact, the checklist won't reappear even though `hasCustomer` would now report `false`, since dismissal isn't re-evaluated once persisted; this matches the manual Dismiss button's own semantics (a user's "stop showing me this" is durable, not re-triggered by later data changes) and wasn't flagged as wrong by any reviewer, just noted. (2) The three checklist items are hand-enumerated in both `DashboardService` and `setup-checklist.tsx` with no shared contract between them — fine at three items, would be worth a shared `packages/shared` list if a fourth item (e.g. "first invoice," once Invoices exists) gets added later.
- **Verified live**: signed up a fresh user/org, confirmed `GET /dashboard/checklist` starts all-false; created a real contact, catalog item, and quote (draft) and confirmed the flags flip on individually and only once the quote is actually sent (not while still a draft); confirmed `POST /dashboard/checklist/dismiss` persists and `GET` reflects it afterward. `pnpm typecheck`/`lint`/`build` all pass clean across `@spine/api`/`@spine/web`. ### 2026-08-08 — Fix the production Docker stack (never actually worked end-to-end until now)

- User asked to review the README's dev setup instructions for completeness; that led to finding two real, pre-existing production-blocking bugs while manually running `docker compose --profile minimal up` for the first time in this project's history (`docker-compose.yml`'s production path had never been exercised end-to-end before). This only ever worked in dev because `nest start --watch`/Next.js both transpile `.ts` on the fly — the packaged, `node`-only runtime can't. (A comment already in `packages/shared/tsconfig.json`, written when this first bit `apps/api`'s dev runtime, documents half of this same root cause but the production/compiled-runtime half was never actually fixed.) Fixed by giving `@spine/shared` a real build step: `tsconfig.build.json` (emits to `dist/`, `rewriteRelativeImportExtensions` so the `.ts`-suffixed internal imports resolve as `.js` in the compiled output), a `build` script, `package.json`'s `main`/`types`/`exports` repointed at `dist/`, `turbo.json`'s `dev` task given `dependsOn: ["^build"]` so a fresh `pnpm install && pnpm dev` builds `@spine/shared` automatically instead of breaking immediately, and `docker/Dockerfile.api` now runs `pnpm --filter @spine/shared build` explicitly before `pnpm --filter @spine/api build` (the api's own `nest build` script has no notion of building its workspace dependencies). `@spine/ui` didn't need the same treatment — `apps/web`'s Next.js build already bundles it from source via `transpilePackages`, and web has no compiled-`node`-only runtime step the way the API does.

### 2026-08-08 — Fix a React key warning in Table's grouped-row mode (user-reported)

- User reported a browser console error: `Each child in a list should have a unique "key" prop` on `quotes-table.tsx`'s use of the new `Table`/`DataTable` `groupBy` mode (added for item 4's version-grouping, user feedback session). - Fixed by switching to the explicit `<Fragment key={group.key}>` form (imported from `react`) and removing the now-redundant `key` from the inner `<tr>` (it isn't itself part of an array being mapped, so it never needed one).
- **Verified**: `pnpm --filter @spine/ui typecheck`/`lint` and `pnpm --filter @spine/web typecheck`/`build` all pass clean. **Not verified**: the browser console itself wasn't re-checked for the warning's absence (no browser automation tooling in this environment) — the fix is a direct, mechanical correction of a well-understood React requirement (a fragment returned from `.map()` needs the same explicit-key treatment as any other list-returned element), not something ambiguous enough to need runtime confirmation beyond the type/build checks already run.

A line could end up mislabeled with a currency its amount was never actually computed in. Fixed: the persisted `unitPriceCurrency` is now always forced to the quote's own `currency`, never trusted from the client — correct per CLAUDE.md's v1 no-multi-currency non-goal, since a line can never legitimately differ from its own document's currency.
  2. **Stale discount approval survives a line edit**: `update()` recomputed `discountRequiresApproval` on every line change but never cleared `approvedByUserId`/`approvedAt` — an owner's approval of a 25% discount would silently still count as approval after staff raised it to 40%, since `send()` only checks `discountRequiresApproval && !approvedByUserId`. Fixed: any edit to `lines` now clears both fields, requiring fresh approval before the draft can be sent again (S-03.9).
  3. **`send()`/`revise()`/`approveDiscount()` raced on their own status guards**: each read-checked the quote's status *before* opening its transaction, then wrote unconditionally inside it — two concurrent calls (e.g. two staff both clicking "send") could both pass the guard. For `send()` specifically this meant two gapless numbers allocated but only one stored (the loser's orphaned, a visible gap in the sequence) and two "sent" audit rows for one send; for `revise()`, two competing next-version drafts (`quotes_parent_idx` is a plain, non-unique index, so nothing at the DB level blocked it either). Fixed: all three methods now re-select the quote with `.for("update")` *inside* the transaction and run every guard against that locked row, mirroring `NumberingService.allocateNumber`'s own established row-lock pattern.
  4. **`AuditLogService.diffFields` crashed on `update()`'s own real code path** (not just a review nit — this one only surfaced by actually exercising `update()` against a live line edit during the fixes above): `input` still contained `lines` (an array with bigint `unitPriceAmount` fields) when passed into `diffFields(existing, input)`. Since `quotes` has no `lines` column, this always produced a nonsensical `"lines: undefined -> [...]"` change entry *and* that entry's bigint failed to `JSON.stringify` into `audit_log.changes` (a jsonb column) — every `PUT /quotes/:id` that touched lines would throw. Fixed by destructuring `lines` out before diffing, mirroring exactly how `contacts.service.ts`'s own `update()` already excludes `contactPersons`/`addresses` for the identical two reasons (not a real column, not diffable/serializable as a scalar).
  - **Re-verified live** against the real local dev Postgres after all four fixes, via a temporary in-process script (`QuotesService` instantiated directly, not through HTTP) exercising: a line with a deliberately mismatched `unitPriceCurrency` (confirmed normalized to the quote's currency in the persisted row), approve → edit lines → confirm `approvedByUserId` cleared → confirm `send()` now correctly re-blocks on the stale-cleared approval, a normal `send()` (confirmed real gapless number `QUO-0001` allocated) followed by a second `send()` on the same now-sent quote (confirmed cleanly rejected, proving the in-transaction re-check fires), and a `revise()` followed by a second `revise()` on the same quote (confirmed cleanly rejected). All six checks passed. The script and its test rows were deleted/cleaned up afterward — nothing left in the dev DB. `pnpm typecheck`/`lint`/`build` re-run clean across `@spine/shared`/`@spine/api`/`@spine/web` after the fixes (same clean result as the pre-fix run above, now covering the corrected code).
  - True concurrent-request races (two simultaneous HTTP calls hitting the row lock at the same instant) were not reproduced under actual concurrency — verifying the lock exists and the guards now run inside it, plus the sequential double-call rejections above, is the practical verification available without a load-testing harness in this environment; the row-lock pattern itself is identical to `NumberingService.allocateNumber`'s own already-relied-upon mechanism.
