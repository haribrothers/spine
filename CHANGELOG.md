### 2026-08-06 — First-run onboarding wizard shell (API + web), and two real signup bugs fixed along the way

- **Bug fix #1 — chart of accounts was never seeded for a real signup.** `seedChartOfAccounts` was only ever called from the standalone seed script; the real `databaseHooks.user.create.after` hook in `apps/api/src/auth/auth.ts` created the org but never seeded its accounts, so every real user who signed up got zero accounts — silently breaking the ledger and this wizard's CoA-review step. Wired the seed call into the hook itself, right after `auth.api.createOrganization`. The seed script (`apps/api/src/db/seed/index.ts`) no longer calls `seedChartOfAccounts` explicitly since the hook now covers it — confirmed by re-running `db:seed:dev` and checking the seeded org still has a full CoA.
- **Bug fix #2 — `session.activeOrganizationId` stayed `null` after every signup.** `auth.api.createOrganization` creates the org/membership rows but never sets the *session's* active org — Better Auth's organization plugin marks that field `input: false` on session schema, so a `databaseHooks.session.create.before` mutation of the payload is silently dropped by Better Auth's own field filtering (confirmed by tracing `crud-org.mjs`/`organization.mjs` in `better-auth`'s compiled output and reproducing against a live signup with curl). Without this, `@OrgRoles()` (from `@thallesp/nestjs-better-auth`, which requires an active org on the session) would 403 every onboarding-wizard call for a brand-new owner. Fixed with a `databaseHooks.session.create.after` hook that looks up the user's org membership and directly `UPDATE`s the just-created `session` row's `active_organization_id` via Drizzle, bypassing the field filter entirely. Verified end-to-end: a fresh `sign-up/email` curl call now returns `get-session` with `activeOrganizationId` populated on the very first session.
- API: real NestJS controllers/services in `apps/api/src/modules/org/` (`SettingsController`/`SettingsService` over the existing generic `settings` key/value table — documented key shapes for `business_profile`, `industry_template`, `currency`, `financial_year_start`, `default_tax_rate`, `onboarding_status`, `dashboard_checklist_dismissed` inline in `settings.service.ts`; `AccountsController`/`AccountsService` for CoA list-grouped-by-type + rename-non-system-accounts; `InvitationsController` wrapping Better Auth's own `auth.api.createInvitation`), plus `apps/api/src/modules/numbering/` (`NumberingController`/`NumberingService` upserting `number_sequences` rows for the six canonical document types from §14.3 — quote/invoice/credit_note/receipt/expense/job; vendor bill excluded since its number is user-entered) and `apps/api/src/modules/tax/` (`TaxController`, a thin wrapper over `SettingsService` for the single default tax rate). Every mutating endpoint requires `@OrgRoles(["owner"])` — server-side, reading the session's actual org member role, never a client claim — and only owners can complete onboarding steps affecting org config.
- **First idempotency-key implementation in the codebase** — `apps/api/src/common/idempotency.interceptor.ts` plus a new `idempotency_keys` table (`apps/api/src/db/schema/idempotency.ts`), keyed on `(orgId, endpoint, key)`. A required `Idempotency-Key` header; a replayed request with the same key returns the stored response instead of re-executing; a concurrent duplicate gets a 409 rather than racing. Nothing else in the API had established this pattern yet (grepped for "idempotency" across `apps/api/src` — no hits before this), so this is a first-of-its-kind implementation worth reviewing rather than a copy of an existing convention. Applied to every mutating onboarding endpoint via `@UseInterceptors(IdempotencyInterceptor)`.

### 2026-08-06 — Web-side Better Auth wiring: sign-up/login UI, session middleware, and a base-URL fix

### 2026-08-06 — Hand-rolled Outlook-style Calendar component
- `@spine/ui`'s `Calendar` (`packages/ui/src/components/calendar.tsx`): Day/Week/Month/Agenda views, click-drag to create an event, drag-move, drag-resize (Day/Week edges), all-day and multi-day events, side-by-side overlap layout, simple daily/weekly/monthly recurrence (end by date or occurrence count, whole-series edits only, no per-occurrence exceptions), and a fixed 8-color category palette — built from native pointer events (`onPointerDown`/`onPointerMove`/`onPointerUp` + pointer capture), not the HTML5 DnD API and not a wrapped calendar library, per explicit direction. `date-fns` added as `@spine/ui`'s first date-math dependency for week/month boundaries and recurrence-rule arithmetic (DST/month-length correctness delegated to it, never hand-rolled).
- Two pure-logic algorithms in the new `packages/ui/src/lib/calendar-utils.ts`: `expandRecurringEvent`/`expandEventsInRange` (walks a recurrence rule forward from its start date via `date-fns` interval addition, stopping at the count/date end condition or once occurrences pass the visible range, capped at 2000 occurrences against pathological rules) and `layoutOverlappingEvents` (single-pass greedy column assignment — sorted by start then by longer-duration-first, each event takes the lowest free column, and every event in a connected overlap cluster reports the cluster's peak concurrency as its `columnCount` so proportional widths stay consistent across the whole cluster, not just pairwise).
- The pre-existing month-grid `Calendar` (used internally by `DatePicker`) was renamed to `MiniCalendar` and extracted to its own file, `packages/ui/src/components/calendar-mini.tsx`, to free up the `Calendar` export name for the new scheduling component and avoid a self-import; `DatePicker` and the new `Calendar`'s toolbar mini-month-picker both consume it unchanged, per the reuse-don't-rebuild instruction. `MiniCalendarProps` renamed to match.
- New design tokens: an 8-color `category-*`/`category-*-bg` palette (blue/green/amber/red/purple/teal/pink/slate) added to `docs/DESIGN.md` and `packages/config/tailwind-preset.css` for both light and dark mode, deliberately a separate layer from the reserved paid/due-soon/overdue/draft financial-status palette even though some hues are shared — an event's color is a free user label, not a system-derived fact, so Calendar is the only component allowed to read these tokens for categorization.
- Full doc page at `apps/design-system/src/app/components/calendar/page.tsx` on the standard 5-section template (Features/Anatomy/API Reference/Examples/Accessibility), added to `nav.ts` under Data display, with job-site-flavored sample event data (site visits, quote reviews, invoice-due markers, a recurring daily standup and monthly invoicing run) per `docs/spine-prd.md`'s domain.
- Fixed three real bugs found during Playwright-driven interactive verification (not just typecheck/lint): (1) Month view's week rows were all rendering at the same vertical offset instead of stacking — a `grid-rows-[repeat(auto-fill,minmax(0,1fr))]` container without matching `grid-template-columns` doesn't reliably auto-place multi-item rows, replaced with a plain flex column of per-week grid rows; (2) drag-to-create never fired because the empty-slot `onPointerDown` guard (`e.target === e.currentTarget`) was always false — the hour-divider children absorbed every pointer event — fixed by making those dividers `pointer-events-none`; (3) a React 19 "setState while rendering a different component" warning from committing `onSlotCreate`/`onEventUpdate` (which set state on the parent `Calendar`) from inside a `setDrag` state-updater callback in `TimeGrid` — fixed by reading the finished drag from a ref instead of the updater's `prev` argument.
