# Changelog

Tracks what's been built and what's next, phase by phase per `docs/spine-prd.md` §12. Update this file as work lands — newest entry on top within each section. This is the progress log; `CLAUDE.md` is the architecture/rules reference.

## Status

**Current phase:** Phase 0 · Foundation is functionally complete (monorepo scaffold, Docker Compose shape, the money/tax core in `@spine/shared`, the full Postgres/Drizzle schema with a working DB-enforced ledger, a documented local dev workflow, a project README, auth (Better Auth: email/password + organizations + JWT), the design system (`docs/DESIGN.md` + `apps/design-system`), the full PRD §F0 `@spine/ui` set plus the complete Radix Primitives + shadcn/ui component union, a hand-rolled Outlook-style `Calendar` component, full `apps/design-system` documentation coverage, the first-run onboarding wizard (now with a real logo upload, not just a URL field), a real Settings UI, a shared `AppShell`, a real S3/MinIO-backed Files module, a GitHub Actions CI pipeline (lint/typecheck/build/unit/integration, the latter against a real Postgres service container), and a formal WCAG 2.1 AA accessibility audit-and-fix pass across all 69 `@spine/ui` components). **Phase 1 · Sales Spine is underway**: Contacts & CRM (F1) and Catalogue (F2) are both built on top of that foundation — F1 since redesigned/expanded (stat cards, multi-view list, tabbed detail page, file/logo upload, tax ID/website fields) beyond its original MUST-level scope; F2 is a flat CRUD module deliberately kept proportionate to its own scope. Quotes (F3) is next and now unblocked (its line items depend on Catalogue's items existing).

Flagged here rather than fixed because it's pre-existing (present before this session's changes) and this task's brief explicitly scoped Contacts' existing CRUD logic as untouchable beyond the two new fields and the array filter.
- MinIO's `spine` bucket isn't provisioned by `docker-compose.dev.yml`/the prod compose file — `FilesService` now self-heals this on first upload (`HeadBucket` → `CreateBucket` on 404, cached after), so no manual `mc mb` step is required, but a `docker-compose` `minio-init` sidecar (the more conventional pattern) would still be cleaner long-term than a lazy per-process check.

### 2026-08-06 — Formal WCAG 2.1 AA accessibility audit-and-fix pass across `@spine/ui`

- The audit-and-fix pass from "Next up" above (`A formal accessibility (WCAG 2.1 AA) pass per component`), now resolved and removed from that list. Scope: all 69 components in `packages/ui/src/components/`, plus the design-token layer they draw from (`packages/config/tailwind-preset.css`) and `docs/DESIGN.md`'s spec. `apps/api` was not touched (out of scope per the task brief); `apps/design-system` doc pages were updated only where a component's API/behavior genuinely changed.
- **Contrast, token-level (the highest-leverage fixes — one CSS value change cascades to every consumer)**: computed real WCAG contrast ratios (relative-luminance formula, not eyeballed) for every text/background token pair declared in `packages/config/tailwind-preset.css`, in both light and dark mode. Six light-mode pairs failed the 4.5:1 body-text minimum and are now fixed at the token level (dark mode was already compliant everywhere checked):
  - `--color-neutral-500` (backs `--color-on-surface-muted`, used across 43 component files, and `--color-draft`): `#8a8578` → `#726c5a`. Was 3.68:1 on `--color-surface` and 3.26:1 on `--color-draft-bg` — both real, live failures on every muted/secondary text label and every "Draft" status chip in the app. Now 5.24:1 / 4.64:1 (worst case).
  - `--color-paid`: `#1a7f4b` → `#177044` (was 4.44:1 on `--color-paid-bg`, now 5.40:1) — StatusChip's "Paid" chip renders at 12px, so the 4.5:1 threshold applies in full (no large-text exception).
  - `--color-category-teal`: `#0f7c7c` → `#0d6e6e` (was 4.41:1 on its `-bg`, now 5.33:1) — `calendar.tsx` renders event-title text in this color.
  - `--color-category-pink`: `#c4408a` → `#a63571` (was 3.93:1, now 5.19:1) — same calendar usage.
  - `docs/DESIGN.md`'s own color spec table updated to match every changed hex, with an inline comment recording the before/after ratio, so the doc and the shipped CSS custom properties stay in sync (they'd drifted apart before: the doc asserted "financial-status colors are independently verified per mode for 4.5:1" while `draft`/`paid`/`category-teal`/`category-pink` in light mode did not actually clear it).
- **A real, live dark-mode bug in Toast/Tooltip — not a contrast tweak, a broken pairing**: `toast.tsx` and `tooltip.tsx` both used `bg-neutral-900` + hardcoded `text-white`/`text-neutral-300`/`text-neutral-400`, intending permanently-dark chrome regardless of the app's theme (matching `docs/DESIGN.md`'s own toast/tooltip spec: `backgroundColor: neutral-900, textColor: #FFFFFF`). But `--color-neutral-900` is theme-*reactive* — it's also `--color-on-surface`, so in dark mode it resolves to `#f3f2ee` (near-white). White text on that background computed to **1.12:1** — every toast and every tooltip in the entire app was effectively unreadable in dark mode. Fixed by introducing three new theme-*invariant* tokens (`--color-inverse-surface: #211f1a`, `--color-inverse-on-surface: #ffffff`, `--color-inverse-on-surface-muted: #d3d0c9`, declared once in `:root` with no dark-mode override, so they hold the same value in both themes) and repointing both components at them instead of the reactive `neutral-900`/hardcoded whites. Also added a missing focus-visible ring to `ToastClose` while in that file (it had none).
- **Other real per-component fixes** (grouped by category; each verified against Radix's own source/types first, per the task's "don't add ARIA that duplicates what Radix already provides" instruction, so these are gaps Radix genuinely leaves to the wrapper):
  - *Forms*: `FormField`'s render-prop previously dropped `required` entirely — a screen reader user had no way to know a field was required beyond a purely visual asterisk. Now passes `aria-required`/`required`/`aria-invalid` through to the control, and the visual asterisk is `aria-hidden` (decorative only, not the sole carrier of the information). `HelperText` now sets `role="alert"` when rendering an error, so validation messages are announced when they appear. `Input`/`Textarea`/`MoneyInput` now self-set `aria-invalid` from their existing `error` prop when the caller doesn't pass `aria-invalid` explicitly (previously `error` only changed the border color).
  - *Custom listbox-style pickers with no Radix Combobox primitive underneath* (`Combobox`, `MultiSelect` — composed from Popover + cmdk/a hand-rolled listbox, not Radix's own Combobox, which doesn't exist) and `DatePicker`: trigger buttons were missing `aria-expanded`/`aria-haspopup`, so assistive tech had no way to know these were disclosure triggers or whether they were open. Fixed on all three.
  - *`calendar-mini.tsx` (hand-rolled, no Radix primitive)*: day-grid cells and the prev/next-month buttons had zero focus-visible treatment at all; no `aria-current="date"` for today; no `aria-selected` for the selected day (color alone conveyed selection); day buttons' only accessible name was the bare day-of-month number ("14"), no month/year/weekday context. Added `role="grid"`/`role="gridcell"`, full `aria-label`s (e.g. "Tuesday, August 4, 2026"), `aria-current`/`aria-selected`, and focus-visible rings throughout.
  - *`calendar.tsx` (hand-rolled Outlook-style scheduler, no Radix primitive)*: already had solid keyboard support in most places (roving-tabindex month grid with arrow keys, `role="button"`+`onKeyDown` event blocks with full `aria-label`s, `aria-pressed` color swatches) — two real gaps found and fixed: the month-view day-number button and per-day event-chip buttons had no focus-visible ring of their own (relying on inconsistent browser defaults against tinted backgrounds).
  - *`Sidebar`'s `SidebarNavItem` and `AppShell`'s `AppShellSidebar`*: when the sidebar is collapsed to its icon-only rail, the text label was fully unmounted (`{!collapsed && <span>...}`), leaving a collapsed nav item with zero accessible name — an icon with nothing for a screen reader to announce. Fixed in both call sites by keeping the label in the DOM with `sr-only` instead of unmounting it.
  - *`Table`'s sortable column headers*: no `aria-sort` on the `<th>` (so the current sort direction wasn't exposed to assistive tech) and no focus-visible ring on the sort button. Both fixed. `Pagination`'s prev/next/page-number buttons had no focus-visible ring at all — fixed.
  - *`Breadcrumb`*: the current/last crumb had no `aria-current="page"` (only a visual font-weight difference); its links had no focus-visible ring. Both fixed.
  - *Missing focus-visible rings on several Radix-wrapped triggers that had `outline-none`/`focus:outline-none` with no replacement*: `NavigationMenuTrigger`, `MenubarTrigger` (both real gaps — Tab-focusing an unopened trigger had zero visible indicator), `AccordionTrigger`, `TabsTrigger`/`TabsContent`, `PasswordToggleFieldToggle`, `ResizableHandle` (a 1px-wide drag handle, given `focus-visible:bg-primary` rather than a ring — a ring reads oddly on something that thin; `react-resizable-panels` itself already supplies `role="separator"`/`aria-valuenow`/keyboard arrow-key resizing, confirmed by reading its source, so only the missing visual indicator needed fixing).
  - *`Spinner`*: `aria-label="Loading"` was set directly on the bare `<svg>` (via lucide's `Loader2`) — an SVG has no implicit ARIA role, so an `aria-label` there isn't reliably exposed as an accessible name by every screen reader. Now wrapped in a `role="status"` span carrying the label (default "Loading", now an overridable `label` prop), with the icon itself `aria-hidden`.
  - *`Alert`*: all four variants (info/warning/critical/success) share the exact same `text-on-surface` text color — only the background tint differs — and `icon` was optional with no default; a `grep` across `apps/web` confirmed every real call site (`team-pane`, `signup`, `contacts-explorer`, `contact-detail` ×2, `contact-form`, `login`, `business-profile-step`, `invite-team-step`) omits the icon prop, meaning every error/warning banner in the shipped app was conveying its severity by background color alone. Fixed by giving `Alert` a default icon per variant (Info/AlertTriangle/AlertCircle/CheckCircle2) that only a `null` icon prop suppresses, plus `role="alert"` for `critical` and `role="status"` for the other three so banners are actually announced.
  - *`Carousel`*: no `role="region"`/`aria-roledescription="carousel"` on the root and no `role="group"`/`aria-roledescription="slide"` on items (a screen reader user had no indication this was a carousel or which slide was showing); embla-carousel's scroll-snap animation duration didn't respect `prefers-reduced-motion` (it's a JS/physics-driven scroll, not a CSS transition, so it's invisible to Tailwind's motion tokens and needed handling via `matchMedia` + Embla's own `duration` option). Both fixed.
