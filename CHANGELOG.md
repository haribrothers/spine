### 2026-08-06 — Fixed `dark:` utilities never tracking the real theme toggle, and made the toggle a floating button

- **Real bug, not just a follow-up:** the previous entry's dark-mode wiring set `next-themes`' `data-theme` attribute correctly and `packages/config/tailwind-preset.css`'s hand-written `:root[data-theme="dark"] { ... }` token block responded to it correctly — but Tailwind v4's generated `dark:` *utility classes* (used for the logo swap: `dark:hidden` / `hidden dark:block`) are a separate mechanism from that hand-written block and default to `prefers-color-scheme` unless a `@custom-variant dark (...)` is registered. No such registration existed, so `dark:` utilities anywhere in the monorepo were silently still following the OS setting, completely ignoring the in-app toggle — clicking the toggle changed every token-driven color correctly but never the logo. The previous entry's own verification didn't catch this because it checked the hand-written token block, not the generated utility-class behavior, and no browser was available to see the mismatch visually.
- Fixed in one place — `packages/config/tailwind-preset.css` now has `@custom-variant dark ([data-theme="dark"] &);` near the top, before the token declarations. This repoints `dark:` for every consumer of the shared preset (`apps/web`, `apps/design-system`, and anything in `packages/ui` that ever uses a `dark:` utility), not just the logo call sites, so this class of bug can't resurface elsewhere.
- `apps/web/src/components/theme-toggle.tsx`: per explicit request, changed from an inline icon button (sitting next to the logo in each page's header row) to a floating button — `fixed bottom-6 right-6 z-50`, a circular `rounded-full` surface with a border and shadow so it reads as an overlay control rather than part of the page flow. Left the `<ThemeToggle />` element in its existing JSX position in each of the four pages (`/login`, `/signup`, `/onboarding`, `/dashboard`) since `fixed` positioning makes DOM placement irrelevant to where it renders — moving it would have been pure churn for no visual change.
- Verified: `pnpm --filter @spine/web typecheck`/`lint`/`build` and `pnpm --filter @spine/design-system build` all clean (the preset is shared, so both consumers were checked, not just the one that surfaced the bug). Confirmed the fix from source through render: found the correct `@custom-variant` syntax for Tailwind v4 by trial (an initial `&:where(A, B)` form failed to parse — Lightning CSS wanted `&` used differently; `([data-theme="dark"] &)` compiled cleanly). Restarted the `apps/web` dev server (a stray production `pnpm build` had clobbered its dev-mode `.next` cache, an unrelated tooling hiccup, not a symptom of this fix) and curled `/login` and `/signup`: rendered HTML shows the logo `<img>` tags with unchanged `dark:hidden`/`hidden dark:block` classes (markup itself needed no changes — only the CSS variant registration was broken) and the floating-button classes on the toggle. Fetched the actual compiled `/_next/static/css/app/layout.css` and confirmed the generated rules are now `.dark\:hidden:where([data-theme="dark"] *, [data-theme="dark"]) { display: none; }` and the `.dark\:block` equivalent — selecting on the attribute `next-themes` actually sets, not `prefers-color-scheme`. Same no-flash-script check as the prior entry reconfirmed the attribute/default-theme config is unchanged. Full visual click-and-watch-it-flip verification still wasn't possible without browser tooling — the compiled-CSS-selector check is the closest available substitute, same caveat as every prior entry this session.
