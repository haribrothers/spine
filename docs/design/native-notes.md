# Native implementation notes (`packages/ui-native`, Expo apps)

Hard-won rules for the native component library and the Expo apps, moved verbatim from the original `CLAUDE.md` (decision D-039). Read before touching `packages/ui-native`, `apps/mobile`, `apps/showcase-native` or `apps/design-system-native`. Where a note describes `apps/mobile` still using React Navigation and `FloatingTabBar`, D-022 now says `apps/mobile` migrates to expo-router native tabs (US-MOB-19); the notes stay accurate for the doc apps and as history.

- **A new native app should be created via `node scripts/create-native-app.mjs <name> [--router=react-navigation|expo-router] [--web]`**, not scaffolded by hand or by copying another app's files. It generates every file in the setup surface (tailwind config wired to `@spine/ui-native/tailwind-preset`, root layout wired to `SpineUIProvider`, theme-storage, jest config, babel/metro/eslint/tsconfig, `nativewind-env.d.ts`, `package.json`/`app.json`) with dependency versions read from `packages/ui-native/package.json`'s own `peerDependencies`, so a new app can't drift from what the library actually expects. See `packages/ui-native/README.md` for the full flag reference and what it does/doesn't cover (it does not scaffold binary assets or merge into an existing app). The README's map of `@spine/ui-native`'s subpath exports (root, `/tokens`, `/tailwind-preset`, `/navigation`, `/jest-config-base`) and each piece's purpose — `SpineUIProvider` (theme + safe-area + status-bar in one call), the `tailwind-preset`'s `themeExtend` (do NOT hand-roll `flatColors`/`flatDarkColors` helpers per app — see the dark-mode bullet below for why that duplication existed and was removed), `jest-config-base` — is the reference if you ever need to wire this up manually (e.g. adding the pattern to an app that predates the script). `apps/mobile`, `apps/design-system-native`, and `apps/showcase-native` all follow this pattern now.
- **`packages/ui-native` has its own equivalent doc app: `apps/design-system-native`** (an Expo/React Navigation app, not a web/Next.js one — `ui-native` components render RN primitives via NativeWind `className`, which don't render in a browser DOM, so they can't be shown in the existing web `apps/design-system`). Same rule as web: every `packages/ui-native` component change ships with its doc screen under `apps/design-system-native/app/components/<name>.tsx`, using the shared doc-page primitives in `src/components/doc-page.tsx` (`DocTitle`/`DocLead`/`DocSection`/`DocSubsection`/`FeatureList`/`ApiTable`) plus `ComponentPreview`/`CodeBlock` for live previews and code snippets — the same Title/Lead/Preview/Features/Anatomy/API Reference/Examples/Accessibility structure `apps/design-system`'s own component pages use, RN-rendered instead of DOM. Register the new screen in **two** places in the same change: `src/lib/component-registry.ts` (nav metadata) and `src/lib/component-screens.ts` (the slug→screen map both shells render from). Run it via `pnpm dev:ui-native` (or `--ios`/`--android`/`--web` variants), which launches Expo like `apps/mobile` does.
- **`apps/design-system-native` renders one of two shells based on viewport width, not platform** (`src/lib/use-is-desktop-layout.ts`, a 768px `useWindowDimensions` breakpoint) — deliberately width-based rather than `Platform.OS`-based, so a narrowed desktop browser window gets the same mobile layout a phone does, matching how a responsive web page behaves. **Desktop (≥768px)**: `src/components/desktop-shell.tsx` — a persistent top bar (`desktop-top-bar.tsx`) + sidebar (`desktop-sidebar.tsx`) + content pane, mirroring `apps/design-system`'s `DocsShell`/`Sidebar`/`TopBar` look. Selection there is local `useState` in `DesktopShell`, not React Navigation — a single-pane desktop layout has no page transition to model, so there's no navigator involved on that branch at all. **Mobile (<768px)**: `src/navigation/root-navigator.tsx`'s existing stack (Home list → push Component detail) — this is the only place React Navigation is used. Both shells render the exact same per-component screen component from `component-screens.ts`; only the surrounding chrome differs.
- **`DesktopSidebar`'s width is a plain inline `style`, not a NativeWind `w-56`/`shrink-0` className** — confirmed by inspecting a real `expo export --platform web` bundle that those classNames were silently dropped from the compiled CSS on `ScrollView` specifically, causing the sidebar to stretch full-width instead of staying at 224px. Don't "clean this up" back into a className if you touch this file; the inline style is the fix, not a stopgap.
- **`lucide-react-native`** (+ its peer `react-native-svg`) is the icon library across `packages/ui-native` and every consuming app — the same icon set web's `packages/ui` uses via `lucide-react`, for real cross-platform visual consistency. This REPLACED `@expo/vector-icons`' `Feather` (removed entirely, confirmed via a repo-wide grep before considering the migration done) after a real, user-reported bug: Feather's icon-FONT glyphs have inconsistent internal vertical centering per icon, which showed up as icons across different tabs sitting at visibly different heights despite an identical declared `size` — confirmed via a live headless-browser measurement (`getBoundingClientRect()` on each tab's icon) showing different `top` values before the migration, and IDENTICAL `top`/`height` for every icon after it, since Lucide's SVG icons have a uniform, predictable bounding box. **Always import each icon via its per-icon subpath** (`import House from "lucide-react-native/icons/house"`), never the bare-package barrel import (`import { Home } from "lucide-react-native"`) — confirmed directly in a real compiled bundle that the barrel import pulls in the ENTIRE icon set (1892 icons, "LucideAArrowDown" etc. all present) regardless of which few are actually used, ballooning `apps/design-system-native`'s bundle from ~1MB to ~2.9MB; the subpath form tree-shakes correctly (verified: only the actually-imported icon names remain in the compiled bundle). Icon size is 24pt across the design system (Lucide's own natural default), a deliberate 1pt departure from iOS's 25pt `UITabBarItem` default — see `floating-tab-bar.tsx`'s own doc comment. Canonical icon names sometimes differ from casual naming: Lucide's "home" icon is canonically `House` (importable as `lucide-react-native/icons/house`; `home`/`Home` exist only as re-export aliases with an extra indirection) — this codebase imports the canonical name directly. `apps/design-system-native`'s theme toggle (`theme-toggle.tsx`, `Sun`/`Moon`/`Monitor`: **sun = light, moon = dark, monitor = system** — three states, not web's two, since `ui-native`'s `ThemeProvider` is deliberately three-state; the icon shows the CURRENT preference, not the state pressing it switches to — an earlier version had this scrambled, fixed 2026-08-30) and its search button (`desktop-top-bar.tsx`/`root-navigator.tsx`'s `SearchButton`, `Search` icon) both use this pattern. `apps/design-system`'s `SearchPalette` uses `cmdk`, which is DOM-only (web-specific portal/keyboard behavior) — `search-palette.tsx` re-implements the same "type to filter, press to select" UX with RN's `Modal`/`TextInput`/`FlatList` instead of porting the library, filtering the same `component-registry.ts` list both shells already share. Cmd/Ctrl+K global capture is wired via a `Platform.OS === "web"`-gated `document.addEventListener` — native has no hardware-keyboard-driven command-palette convention, so native users open it via the search button only.
- **Jest can't load `lucide-react-native` out of the box in any app/package that renders it — this is a shared Jest config fix, not a per-app workaround.** `@react-native/jest-preset`'s test environment sets `customExportConditions = ['require', 'react-native']`; both conditions match Lucide's `package.json` `exports` map, and its `"react-native"` condition (an ESM-only `.mjs` build) wins over `"require"` (its CJS build) — Jest's CJS-based runtime can't `require()` an ESM file (`SyntaxError: Unexpected token 'export'`). Fixed by overriding `testEnvironmentOptions.customExportConditions: ["require"]`, forcing Jest to resolve the CJS build. This is scoped to Jest's own module resolution only — Metro (the real app/Expo bundler) has its own resolver and correctly picks the `"react-native"` condition for actual builds, confirmed unaffected by real `expo export` runs. **The fix now lives once, in `packages/ui-native/jest-config-base.js`** (exported via `@spine/ui-native/jest-config-base`) — `packages/ui-native/jest.config.js` itself extends it, and any future app/package adding a Jest suite that touches Lucide (directly or via a `packages/ui-native` component) should extend it too (`module.exports = { ...require("@spine/ui-native/jest-config-base"), ...myOverrides }`) rather than rediscovering this bug from scratch.
- **`packages/ui-native` components must run their final className through `cn` (`src/lib/cn.ts`, clsx + tailwind-merge), never `cva`'s raw output or a plain string/array concatenation, whenever a component composes two independently-conditioned class sets that can touch the same CSS property** (e.g. a `variant` axis and a `disabled` axis both setting a background/text color). `packages/ui`'s Button resolves this on web via Tailwind's `disabled:` pseudo-class, a real specificity bump that wins regardless of source order — NativeWind has no equivalent pseudo-class for `Pressable`, so two same-specificity conflicting utility classes (e.g. a variant's `bg-primary` vs. a disabled override's `bg-transparent`) resolve by Tailwind's build-time CSS-discovery order, NOT by which class appears later in the string. This silently broke Button's disabled-state text (shipped invisible: `<Button disabled>` with the default `primary` variant rendered white text on a transparent background) until fixed by wrapping both `buttonVariants(...)` and `textVariants(...)` calls in `cn(...)`, which deterministically drops the earlier conflicting class. `button.a11y.test.tsx`'s regression test asserts every variant's disabled text className contains `text-on-surface-muted` and never the variant's own text color — follow this same pattern (`cn`-wrap + a regression test asserting the losing class is actually absent, not just that the winning class is present) for any future `ui-native` component with a similar two-independent-conditions composition.
- **Button's `loading` prop has no web `packages/ui` equivalent to mirror — it's a `ui-native`-only addition, and its own follow-on bug is a reminder to re-derive EVERY visual consequence of a state change, not just the one first reported.** `loading` sets `isDisabled` internally, which (correctly, per the fix above) makes the button's background the disabled look (`bg-transparent`) regardless of variant — but the `ActivityIndicator`'s `color` prop was still hardcoded to `#FFFFFF` for `primary`/`danger` from before the disabled-text fix landed, so the spinner was invisible against its own now-transparent background (a second real shipped bug, found right after the first). Fixed by resolving the spinner's color from `nativewind`'s `useColorScheme()` against `lightColors.onSurfaceMuted`/`darkColors.onSurfaceMuted` — the same color the disabled label text uses — instead of a variant-conditioned hardcoded hex. `button.a11y.test.tsx` has a matching regression test (`UNSAFE_getByType(ActivityIndicator)`, asserting `color` is never `#FFFFFF`), confirmed to fail without the fix. Lesson for future `ui-native` work: when a prop changes visual state via a shared flag like `isDisabled`, audit every other prop/element whose value was computed assuming the OLD state (a hardcoded color keyed off `variant` alone, here) — a partial fix that addresses only the originally-reported symptom can leave a sibling bug from the very same root cause.
- **`packages/ui-native`'s dark-mode colors are NOT a `{ DEFAULT, dark }` color-object shape in any `tailwind.config.js` — that shape silently does nothing.** Tailwind's color flattening has no special meaning for a `dark` sub-key (`DEFAULT`/`50`/`100`/.../`900` are the only recognized shapes), so a color defined that way always compiles to ONE fixed light-mode value — confirmed live: with that shape, a real `expo export --platform web` bundle's compiled CSS had ZERO `.dark` selectors anywhere, meaning the light/dark/system toggle changed the `colorScheme` state correctly (that mechanism, `nativewind`'s `colorScheme.set(...)` via `theme-provider.tsx`, was never broken) but nothing on screen ever visibly changed — this shipped and went unnoticed in `apps/mobile` for multiple phases simply because `apps/mobile` had no toggle UI to exercise it until `apps/design-system-native` added one and a user reported it. **The real, working mechanism**: every themed color is registered TWICE — once under its plain name from `lightColors`, once under `<name>-dark` from `darkColors` (e.g. `surface` and `surface-dark`). This flattening now lives in exactly one place, `packages/ui-native/tailwind-preset.js`'s exported `themeExtend`, which every app (`apps/mobile`, `apps/design-system-native`, `apps/showcase-native`) spreads directly into its own `tailwind.config.js`'s `theme.extend` — see `packages/ui-native/README.md`'s "Getting a new app running" section for the exact snippet. Do not hand-roll `flatColors`/`flatDarkColors` helpers per app again; that duplication (and the drift risk of a token added to `tokens/colors.ts` needing manual re-flattening in N places) is exactly what the shared preset exists to kill — and every themed utility class in every component/screen must be written with an explicit paired `dark:` variant of the same base name (`className="bg-surface dark:bg-surface-dark"`, `"text-on-surface-muted dark:text-on-surface-muted-dark"`, etc.), including on `active:`-prefixed classes (`active:bg-surface-sunken active:dark:bg-surface-sunken-dark` — verified this exact stacked-variant ordering compiles to a real rule, not `dark:active:`). This produces genuine NativeWind-compiled `.dark`-scoped CSS rules the runtime toggle can actually switch to, exactly like a standard Tailwind project's own `dark:` classes — verified directly by inspecting compiled CSS output (`.dark\:bg-surface-dark:is(.dark *){...}` present with the correct dark color value) both before and after the full fix. **A hardcoded raw color prop is a separate, easy-to-miss gap this pattern doesn't cover**: `TextField`'s `placeholderTextColor="#726C5A"` is a native RN prop, not a NativeWind className, so it stays the light-mode `onSurfaceMuted` value in dark mode too — same class of gap as Button's `ActivityIndicator` `color` prop (fixed above), not yet fixed here; resolve it the same way (via `useColorScheme()`) if/when it's reported. **When adding any new `packages/ui-native` component or screen, or any new consumer of an existing one, every themed `bg-*`/`text-*`/`border-*` class must get its `dark:*-dark` pair in the same change** — there is no lint/build check that catches a missing pair (unlike the a11y-coverage script below), so this is a discipline rule, not a machine-enforced one; a bare `bg-surface` with no `dark:` pair is not obviously broken by inspection alone (it just always looks like light mode), which is exactly how this shipped unnoticed the first time.
- **`react-native-css-interop@0.2.6`'s web `colorScheme.set("system")` has a real upstream bug: it NEVER actually checks the OS/browser's `prefers-color-scheme` — it unconditionally removes the `.dark` class**, confirmed by reading its own `dist/runtime/web/color-scheme.js` (`set()`'s only special case is `value === "dark"`; every other value, including `"system"`, falls into an unconditional `classList.remove(...)`) and reproduced live with a headless-browser test forcing `prefers-color-scheme: dark` — `.set("system")` still left the page in light mode. **Fix, in `packages/ui-native/src/theme/theme-provider.tsx`**: a web-only `applyPreference` helper that, when `preference === "system"` on `Platform.OS === "web"`, resolves `window.matchMedia("(prefers-color-scheme: dark)")` itself and calls `.set("dark" | "light")` directly — NEVER `.set("system")` on web — plus a live `matchMedia` `change` listener (tracked in a ref and cleaned up on every preference change, not just on unmount, to avoid leaking one listener per toggle click) so an OS-level theme switch while still on "system" is picked up without a reload. Native is unaffected (its `Appearance`-based path doesn't share this bug) and still calls `.set("system")` directly. **The boot-time default matters just as much as the toggle**: the effective preference (`stored ?? "system"`) must be explicitly (re-)applied via this same helper even when `storage.getPreference()` resolves `null` (a fresh session with no saved preference) — the original code only called `nativeWindColorScheme.set(...)` when a STORED value existed, silently leaving NativeWind's own boot-time default (which hits the exact same "system" bug) in effect for every first-time visitor; this was caught only by testing the fresh-session case specifically, after the explicit-toggle case already looked fixed. Verified end-to-end with headless-browser tests covering all three cases: fresh boot with browser set dark, explicit cycle back to "system" with browser set light, and the same cycle with browser set dark — plus a live OS-preference-change simulation while parked on "system".
- **`apps/design-system-native`'s theme preference persists across reloads** (`src/lib/theme-storage.ts`'s `persistentThemeStorage`) — an earlier version used an in-memory-only `ThemeStorage` (reset on every reload), a deliberate initial scoping choice that shipped as a real reported friction point once the toggle was actually used day to day. `expo-secure-store` (what `apps/mobile`'s own `theme-storage.ts` uses) has NO web implementation at all — its `.web.ts` is an empty stub, confirmed by reading the installed package — so this storage branches on `Platform.OS`: `localStorage` on web (a theme preference isn't remotely sensitive, so a bare synchronous browser API is fine; no need for SecureStore's native-only encryption story), `expo-secure-store` on native for consistency with `apps/mobile`'s choice. Verified persistence live with a headless-browser reload test, not just by reading the code.
- **React Navigation's own chrome (native-stack headers, bottom-tab bars, drawer chrome, etc.) is NOT NativeWind-styled and ignores `dark:` classes entirely** — it's rendered by React Navigation itself, outside any app's className-based component tree, and only reacts to the `theme` prop passed to `NavigationContainer` (`@react-navigation/native`'s own `DefaultTheme`/`DarkTheme`, a generic blue/gray palette unrelated to this design system's tokens). This shipped as a real, user-reported bug in `apps/design-system-native`: a dark-mode screenshot showed a correctly-dark body under a still-light header, because `RootNavigator` never passed a `theme` prop at all. Fixed via **`packages/ui-native/src/navigation/navigation-theme.ts`'s `spineLightNavigationTheme`/`spineDarkNavigationTheme`** (built from `lightColors`/`darkColors`, not React Navigation's defaults, and exported from the shared package — via `@spine/ui-native/navigation`, a dedicated subpath export like `./tokens` — rather than duplicated per app, since it's a pure function of the shared color tokens with zero app-specific logic), selected via `useTheme().resolvedMode` and passed to `NavigationContainer`'s `theme` prop. `@react-navigation/native` is an **optional peer dependency** of `packages/ui-native` (not a hard dependency) so apps that don't use React Navigation aren't forced to install it. **`apps/mobile`'s bottom-tab bar was proactively fixed the same way** even before it had a visible dark-mode toggle UI to expose the bug — the exact same gap (`NavigationContainer` with no `theme` prop) was present there too, just latent, and the whole point of finding this bug once is not shipping it twice. **Any future native-stack/tab/drawer screen in either app must pass this same `theme` prop** — pairing `dark:` classes on an app's own View/Text components does nothing for chrome React Navigation renders itself; that chrome needs a `theme` prop (or per-screen `headerStyle`/`headerTintColor` options for one-off overrides), never NativeWind classes.
- **Customizing the bottom tab bar (icons, active/inactive colors, background) belongs in `packages/ui-native/src/navigation/tab-bar.tsx`, not hand-rolled per app** — `spineTabBarScreenOptions(resolvedMode)` returns the shared `screenOptions` (tint colors + `tabBarStyle`, same "raw RN style prop, not a NativeWind className" situation as `navigation-theme.ts`, since React Navigation's tab bar isn't className-styled), and `TabBarIcon` takes a `lucide-react-native` icon COMPONENT directly (`icon={Home}` — from a per-icon subpath import, per the icon-library rule above) rather than a string name, so a typo is a build error, not a silently-blank icon; there is no separate icon-name union type to keep in sync. React Navigation already resolves the correct active/inactive `color` and passes it into `tabBarIcon`; `TabBarIcon` just renders it. Both are exported from the same `@spine/ui-native/navigation` subpath as the nav-theme helpers (`@react-navigation/bottom-tabs` is an additional optional peer dependency of `packages/ui-native`, same pattern as `@react-navigation/native`). Each app still supplies its own per-`Tab.Screen` icon component/title (necessarily per-route) — only the shared theming is centralized. **This is a "style the existing native tab bar" pattern, not a from-scratch custom tab bar component** — deliberately chosen over replacing React Navigation's own tab bar via the `tabBar` prop, so native platform behavior (safe-area insets, gestures, accessibility) stays free. For an actual from-scratch tab bar, see `FloatingTabBar` below.
- **`FloatingTabBar` (`packages/ui-native/src/navigation/floating-tab-bar.tsx`) is the from-scratch custom tab bar** — a GitHub-iOS-style floating, rounded, inset pill (not full-width/flush with the screen edge), every tab's icon stacked above its label, the active tab additionally shown inside its own soft rounded highlight capsule (`colors.infoBg`). Passed via `Tab.Navigator`'s `tabBar` prop, which fully REPLACES React Navigation's default tab bar — unlike `spineTabBarScreenOptions` above, this component is on the hook for everything the native tab bar normally provides for free: safe-area insets (via `BottomTabBarProps.insets`, already resolved by React Navigation — no separate `useSafeAreaInsets` call needed inside the component itself), active-tab detection (`state.index`), reading each screen's `tabBarIcon`/`title` from `descriptors`, press handling replaying the same `tabPress`/`navigate` event contract the default tab bar uses (so re-tap/back-button semantics aren't silently lost), and accessibility roles/state (`accessibilityRole="button"`, `accessibilityState.selected`) by hand. Because it's `position: absolute` (it floats over content instead of reserving its own layout space), every screen needs bottom padding at least `FLOATING_TAB_BAR_RESERVED_HEIGHT` (also exported) tall — passed via `Tab.Navigator`'s `screenOptions.sceneStyle: { paddingBottom: FLOATING_TAB_BAR_RESERVED_HEIGHT + insets.bottom }` in the consuming app, using that app's own `useSafeAreaInsets()` (device-specific, not baked into the constant). `resolvedMode` isn't part of `BottomTabBarProps`, so the consuming app injects it itself: `tabBar={(props) => <FloatingTabBar {...props} resolvedMode={resolvedMode} />}`. **Went through a real layout correction after initial review**: the first version showed the label only on the active tab, in a horizontal icon-then-label row; per an explicit screenshot reference (GitHub's iOS app), the correct layout is icon-above-label on EVERY tab (not just active), which is what shipped — `FLOATING_TAB_BAR_RESERVED_HEIGHT` was bumped 64→76 to fit the taller stacked layout. **A second round of real, user-reported visual bugs followed**: (1) the pill used `rounded-3xl`, a large-radius rounded RECTANGLE, not a true pill — fixed to `rounded-full`; (2) a visible white area appeared behind the floating bar in `apps/design-system-native`'s doc-screen demos specifically — root cause was the demo's own preview `View` (the bordered `h-72 overflow-hidden rounded-lg` box in `app/components/tab-bar.tsx`/`floating-tab-bar.tsx`) having no background color at all, so its rounded corners revealed the page's own white background underneath, AND the demo's nested `NavigationContainer` never received a `theme` prop (same class of bug as the very first nav-theme fix, recurring because these two doc screens' live demos are separate `NavigationContainer` instances from `RootNavigator`'s) — fixed by adding `bg-background dark:bg-background-dark` to both preview boxes and passing `spineLightNavigationTheme`/`spineDarkNavigationTheme` to both demo `NavigationContainer`s. Also added `pointerEvents="box-none"` to `FloatingTabBar`'s outer wrapper (the transparent padding around the pill was otherwise capturing touches meant for content behind it) — found while re-reviewing the component for the pill-shape fix, not separately reported. **Any future live-demo doc screen embedding its own `NavigationContainer` must pass a theme prop and give its preview box a real background — this is now the second time this exact gap has shipped in two different doc screens.** **A third round found the active-tab highlight capsule itself wasn't a true pill**: it used `rounded-2xl` (a small, fixed 16px radius) on an item roughly 65px tall, which reads as a rounded rectangle rather than a smooth pill matching the outer container's curvature — most visible on the rightmost tab, where the highlight's outer corner sits directly against the pill's own rounded edge. Fixed to `rounded-full` (same as the outer pill), which resolves to a true capsule regardless of the item's actual height. Both live demos (`tab-bar.tsx` and `floating-tab-bar.tsx`) were also expanded from 3 to 5 tabs (Home/Jobs/Expenses/Messages/Profile) per explicit request, to better exercise the layout with a realistic tab count. **A fourth round, requested rather than reported as a bug, brought the component to iOS's actual `UITabBar` spec**: height (49pt content height, excluding the home-indicator safe-area inset which is still added separately via `insets.bottom`) and label size (10pt) — all now named constants (`TAB_BAR_HEIGHT`/`TAB_ICON_SIZE`/`TAB_LABEL_FONT_SIZE`) instead of the earlier arbitrary 22px/11px guesses; `FLOATING_TAB_BAR_RESERVED_HEIGHT` is now derived from `TAB_BAR_HEIGHT` rather than a separate hardcoded number. Icon size was requested at 24×24pt specifically (not iOS's own 25pt default) — see `TAB_ICON_SIZE`'s own comment on this deliberate 1pt departure, which happens to also match Lucide's own default icon size. **The active-tab highlight is now a single animated capsule, not each tab's own instant background toggle** — `Animated.Value`s for `x`/`width`, measured per-tab via `onLayout` (stored in a `useRef` map since layout is async and can arrive in any order) and updated with `Animated.spring` whenever `state.index` changes, so selecting a new tab slides the highlight across rather than snapping. The very first layout measurement (initial mount) is special-cased to `setValue` directly rather than animating — animating from an unset `Animated.Value`'s default of 0 would otherwise visibly slide in from the top-left corner on first render. `useNativeDriver: false` is required here (not a shortcut) since `left`/`width` aren't part of the native-driver-supported style-property allowlist (only transforms/opacity are) — this animation runs on the JS thread, which is an acceptable tradeoff for a single infrequent tab-bar transition, not a scroll-linked or high-frequency animation. Verified live with a mid-animation screenshot (captured ~80ms into a Home→Messages transition) showing the highlight genuinely still in flight between positions, not just before/after frames that could hide an instant-snap bug. **A fifth round, a real user-reported bug, fixed icon vertical misalignment** — every tab's icon+label sat at visibly different heights despite identical layout code, root-caused to `@expo/vector-icons`' Feather having inconsistent internal glyph centering per icon (a known icon-font characteristic). Fixed by migrating the whole icon system to `lucide-react-native` (SVG-based, uniform bounding box per icon) — see the icon-library rule above for the full migration (per-icon subpath imports, the `@expo/vector-icons` removal, the Jest `customExportConditions` fix). Confirmed fixed with a real measurement, not just visual inspection: `getBoundingClientRect()` on all 5 tabs' icons showed identical `top` (529px) and `height` (24px) after the migration, vs. differing values before it. **A sixth round, reported on a real iOS simulator specifically, was a DIFFERENT bug the fifth round's fix didn't cover**: "Messages" (tied with "Expenses" for the longest label) sat visibly lower than the other 4 tabs — this was NOT the icon-glyph-alignment bug again; each label `<Text>` had no `numberOfLines`, so on a genuinely narrow screen (a real ~390pt-wide iPhone, not the ~900px-wide desktop-browser window the fifth round's fix was verified against) the widest label(s) could wrap to two lines while shorter ones stayed on one, shifting that tab's whole icon+label block relative to its neighbors (each `Pressable` centers its content as one block). **This is the actual lesson, not just the fix**: the fifth round's headless-browser verification used a viewport far wider than any real phone, so it could not have caught a width-constrained wrapping bug — always verify a mobile component at a REALISTIC narrow width (e.g. 390×844, an iPhone 14-class viewport), not just "some browser window," especially for anything with per-item flex-divided horizontal space and text content. Fixed by adding `numberOfLines={1}` (forbid wrapping) plus `adjustsFontSizeToFit`/`minimumFontScale={0.8}` (shrink slightly rather than clip a genuinely-too-long label, matching iOS's own `UITabBarItem` behavior) to the label `Text` in `floating-tab-bar.tsx`. Re-verified at 390×844 specifically: all 5 tabs' icon `top` and label `top` values were identical afterward, with "Expenses"/"Messages" correctly truncating to "Expens…"/"Messa…" instead of wrapping.
- **`@expo/ui` (installed in `apps/design-system-native` only, SDK 57 — `@expo/ui@~57.0.14` + its `react-native-worklets` peer) is scoped narrowly: it renders real native SwiftUI/Jetpack-Compose components, which is the ONLY way to get iOS's genuine liquid-glass material (a real-time system-compositor blur of scrolled content behind a control) — no NativeWind/Tailwind styling reproduces that effect.
