# 07 · Security

## Principles

1. **The server decides.** Every endpoint checks role, capability and ownership server-side. The web and mobile apps only hide what a user can't do; they never grant anything ([D-018](12-decisions.md)).
2. **One list.** The capability list the Teams UI renders and the list the API enforces are the same array (`CAPABILITIES` in `packages/shared/src/schemas/permissions.ts`). A capability in one and not the other is a bug.
3. **Nothing financial is deleted.** Issued documents are voided or credited, never edited or deleted; every create/update/issue/void/delete is in the audit log.
4. **Least exposure on phones.** Field users never see financial reports; Field's rights are fixed and can't be widened by a Team ([D-019](12-decisions.md)).
5. **No mandatory SaaS, no silent calls home.** Telemetry is off by default; the only outbound call is the optional daily update check ([D-055](12-decisions.md)).

## Authentication

| Topic | Rule |
|---|---|
| Method | Email + password (Better Auth). Passwords hashed with Argon2id (`apps/api/src/auth/password.ts`, `@node-rs/argon2`); minimum 8 characters |
| Sign-up | Open only while the instance has no users; the first user becomes Owner and Primary Owner. After that `/signup` shows "This Spine is invite-only" and the API rejects sign-up without a valid pending invitation for that email (Better Auth `user.create.before` hook, US-AUTH-08). `SPINE_ALLOW_OPEN_SIGNUP` opens it for automated tests and is ignored in production |
| Invitations | Created by an Owner (Staff or Field only — never Owner, [D-020](12-decisions.md)); emailed link; accepting requires being signed in with the invited email; expired, cancelled or used invitations show "This invitation can't be used" |
| Password reset | Email link, single-use, expires in 1 hour; resend after 60 s; responses never reveal whether an account exists; a reset signs out every session, web and phone (US-AUTH-09, US-AUTH-10, [D-056](12-decisions.md)). Requests are limited to 10 per IP per 15 minutes (429) and 3 emails per address per hour (silently; the answer is the same) ([D-119](12-decisions.md)). The token is never logged |
| Sessions (web) | HTTP-only session cookie (Better Auth); `Secure` when served over HTTPS; lifetime pinned explicitly in `auth.ts` |
| Sessions (mobile) | Session token in the OS secure store (Keychain / Keystore), sent as Bearer; signing out deletes it and revokes the session |
| Customer | Public quote token: random, unguessable, one quote, 30-day lifetime, rate-limited 20/min/IP ([D-032](12-decisions.md)) |
| 2FA | Not in v1 ([Q-08](13-risks-open-questions.md)) |

## Roles

| Role | Who | Configurable | Notes |
|---|---|---|---|
| Owner | One or more; full access to everything | No | Exactly one **Primary Owner** (DB partial unique index); only they can transfer that flag, and nobody can demote, deactivate or remove them |

| Customer | Quote link holder | — | Reads one quote; accepts or declines while it's `sent` |

## What every member can do without a capability

- Read contacts, catalogue, leads, activities, quotes, jobs (Owner and Staff read everything; Field reads assigned jobs without money and the quotes to present on them — enforced in the service, US-JOB-19). Today several read routes have no role guard at all ("Any member" in [05](05-api.md)); the gaps that matter are closed by US-JOB-19 and US-OPS-20.
- Read a meeting they're allowed to see (`org` visibility, organiser, or invitee) and respond to their own invite.
- Edit their own Profile & Preferences, password, theme, dashboard layout and reminder lead time.
- See the dashboard widgets that need no capability: own overdue follow-ups, upcoming meetings, invoices due this week, milestones due, pipeline by stage, recent activity (filtered to their role).

## Secrets

- Secrets come only from environment variables (`AUTH_SECRET`, `DATABASE_URL`, `SMTP_PASSWORD`, `S3_SECRET_KEY`, `VAPID_PRIVATE_KEY`, `CLOUDFLARE_TUNNEL_TOKEN`); never committed; `.env.example` holds placeholders only.
- `AUTH_SECRET` must be at least 32 random bytes; the install script generates it (US-OPS-01).
- Files are never served directly from the volume or bucket. Every file read is authorised against the record the file belongs to (US-OPS-20), then streamed by the API (`local` driver) or answered with a presigned URL valid for at most 5 minutes (`s3` driver); session-less links are API-signed with `AUTH_SECRET` and expire within 5 minutes.
- Uploads are type-checked from their bytes (JPEG, PNG, WebP, HEIC, PDF), photo GPS data is stripped, paths are built from ids only, and responses carry `nosniff` (US-OPS-29). Checksums detect damage (US-OPS-28); stored files are write-once, so an issued document's PDF can't be replaced (US-INV-17).
- File reads (US-OPS-20, D-117): Owners read every file in their organisation. A file not attached to a record yet is readable only by its uploader and Owners. Staff read every attached file. Field read contact logos and photos, the business logo, members' avatars, photos on jobs they're assigned to, receipts on their own expenses, and quote PDFs for quotes on their assigned jobs — never invoice, credit-note or receipt PDFs. Anything else is a 404. An API-signed link (no screen issues one yet) is checked when it's issued.
- File-storage administration is Owner-only and never Team-configurable: `GET /files/integrity` (the damaged-files warning) and the storage banner show to Owners only; `files_damaged` notifies Owners only; `files:migrate` is a server-side command, not an endpoint. `GET /health/ready` is public and reveals only the storage driver and how full the volume is.
- At rest: full-disk encryption on the host is recommended; per-file encryption with `FILES_ENCRYPTION_KEY` is optional and off by default because losing the key loses every file (D-106). Backups can be encrypted with a passphrase (D-105).

## Destructive actions

| Action | Who | Safeguard |
|---|---|---|
| Delete a draft quote / invoice / bill / credit note | Own/others delete capability | Confirmation naming the document; issued documents can't be deleted |
| Void an invoice or vendor bill | `invoices.void` / `vendor_bills.void` | Reason required; reversing entry; audit log |
| Delete a contact | `contacts.delete_*` | Blocked if it has financial documents; archive offered instead |
| Delete a payment | `payments.delete_*` | Only while unallocated; reversing entry |
| Deactivate a user | Owner | Confirmation; history kept; never the Primary Owner |
| Promote to Owner / demote | Owner | Confirmation (US-TEAM-16); never the Primary Owner |
| Transfer primary ownership | Primary Owner only | Must pick an existing Owner; confirmation |
| Delete all demo data | Owner | Confirmation; removes only `is_demo` rows |
| Close a fiscal period | Owner | Blocks postings inside it; reopenable |

## Data protection and privacy

- All data stays on the self-hoster's server. No analytics or telemetry unless the Owner opts in (none exists in v1).
- The mobile app stores the session token in the secure store and cached job data in its sandbox; signing out clears both after the outbox is empty or the user confirms discarding it.
- Audit log rows record actor, action, record and a field diff; they are never edited.

## Supply chain

- Lockfile committed; `pnpm install --frozen-lockfile` in CI.
- Dependency audit in CI (`pnpm audit --prod`, fails on high/critical) — added in Phase 8 (NFR-SEC-04).
- Docker images pinned to major versions (`postgres:16-alpine`, `caddy:2-alpine`); base images rebuilt per release.

## Appendix — permission model implementation notes (moved verbatim from CLAUDE.md)

Historical text, kept word for word. Where it disagrees with the matrix above, the matrix wins: `meetings.manage` has since been split into `meetings.*` own/others capabilities, and Better Auth is now 1.6 ([01](01-tech-stack.md)).

### Permission model (PRD §2.1) — read before touching auth, roles, or any endpoint's authorization check

- **Roles**: `owner`, `staff`, `field` on `memberships`, plus the external customer link role. Owner and Field are fixed, non-configurable. Staff is subdivided by **Teams** — an org creates named Teams (`teams`), each with a configurable privilege matrix (`team_privileges`, one boolean row per Team per capability). A Staff user can belong to multiple Teams; effective access to a capability is the union across their Teams (most-permissive-wins, no explicit-deny in v1).
- **Primary Owner**: the first signup on a fresh instance. Exactly one per org, enforced by a partial unique index on `memberships.is_primary_owner`, not application logic alone. Cannot be demoted or removed by anyone but themselves, and only via an explicit transfer action — never a side effect of role editing. Signup is single-use: every account after the first is created by invite, never public registration.
- **Multiple Owners**: any Owner can promote a Staff user to Owner. All Owners have equal, unrestricted access — there is no per-owner content ownership or restriction in v1 (see "Deferred to v2" below). **Owner is never granted at invite time** — `POST /org/invitations` rejects `role: "owner"` outright (Better Auth's own `createInvitation` would otherwise allow it); the only path to Owner is `PUT /org/members/:id/promote` on an existing Staff member who has already accepted an invite and joined.
- **Field stays fixed on purpose**: never make Field Team-configurable — it exists specifically so an owner can't accidentally widen a mobile user's access to financial data (protects the "mobile hides all financial reports" rule, PRD §S-11.8).
- **"Manage users, teams, permissions, org settings, tax rules" is Owner-only, not Team-configurable, ever** — it's the one capability that could otherwise grant itself broader access.
- **Single source of truth**: the capability list the permissions UI renders and the list the API enforces per-endpoint must be the same list. If you add a new capability to the privilege matrix UI without a matching server-side check (or vice versa), that's a bug, not a follow-up.
- **Nav placement**: Users/Teams/Permissions management lives in its own top-level, Owner-only sidebar section with real routes — not inside the org Settings dialog. Settings stays for organisation configuration (branding, tax, numbering, business profile, etc.). See PRD §9 FEAT-10 S-10.18.
- **Whenever a new feature changes who-can-do-what** — adds a capability, a resource, or an action that should be gated — update the privilege matrix (the Team-configurable capability list) and this section of CLAUDE.md in the same change. A feature that's gated only in the UI, or only in one layer, is incomplete.
- **`meetings.manage`** (Team-configurable) gates create/update/delete of meetings, replacing an earlier piggyback on `contacts.manage`. It does **not** control who can *see* a given meeting — meeting read-access is a separate, capability-independent check: a meeting's own `visibility` (`private`|`org`) plus its invite list (`meeting_attendees`) decides who can read it via `GET /meetings`/`GET /meetings/:id`, enforced in `MeetingsService` regardless of `meetings.manage`. Owners always see every meeting (private or org) per the blanket-access rule above; Staff/Field only see `org`-visibility meetings or `private` ones they organize or are invited to. Responding to your own invite (`POST /meetings/:id/respond`) requires no capability at all — it's self-service, gated only by having an attendee row. When adding any future meetings-adjacent capability, keep this "manage ≠ can-read" split — don't let a management grant widen read access.
- **Own/others ownership-based capability split — the general pattern, being extended module by module** (PRD §9, e.g. FEAT-01 S-01.15/S-01.16/S-01.17, FEAT-02 S-02.5, FEAT-03 S-03.13). Read is unconditional (no capability gate at all on `GET` routes); write/delete are split into a **four-capability group per resource** — `<resource>.edit_own`/`edit_others`/`delete_own`/`delete_others` — enforced in the SERVICE layer (not the route guard, since ownership depends on the record's `createdByUserId`/equivalent, which isn't known until the record is loaded) via `requireOwnershipCapability` (`apps/api/src/auth/capability.util.ts`), called right after the existing read-before-write lookup in `update`/`archive`/`restore`/`delete`. `<resource>.edit_own` also gates **create** — a Team with neither `edit_own` nor `edit_others` cannot create new records of that type at all, only view existing ones. A Team's grants for one resource are completely independent of every other resource's grants (`contacts.edit_others` implies nothing about `catalog.edit_others`, `quotes.edit_others`, etc.). "Own" means a stable creator/organizer signal, set once and never reassigned — deliberately distinct from a resource's own reassignable people-fields when one exists (`leads.ownerUserId` pipeline rep, `activities.assignedToUserId` delegate, `meetings.organizerUserId` — wait, meetings use organizer AS the ownership signal since there's no separate creator field; the point is: whichever field is chosen as "own" for a resource, it must never silently change just because the record gets reassigned to someone else). A resource with no `createdByUserId`-equivalent column at all (e.g. meetings) uses the closest stable "this person owns/organizes it" field instead — documented per-module. A `null`/unset owner (legacy pre-migration rows) is treated as unowned: only `_others` can touch it, never `_own`, even for the user who might otherwise seem to have created it. **Workflow actions that aren't edits** (send/revise a quote, approve/reject an expense, issue/void an invoice, etc.) get their OWN dedicated capability rather than being folded into `edit_own`/`edit_others` — "can I edit my own draft" and "can I send/approve/void" are different questions an Owner may want to grant separately, and conflating them (e.g. treating an approver's action as if it were "editing the submitter's own record") misrepresents the actual relationship. The seeded "General Staff" default Team grants every one of these capabilities `true` on introduction (preserving pre-split full-access behavior for every existing org via a hand-authored backfill migration, same pattern each time — see `apps/api/drizzle/0036`–`0040` for worked examples) — Owners narrow per-Team afterward if they want a more restrictive split. The Team privilege-matrix UI (`team-detail-view.tsx`) renders each resource's capabilities as a collapsible group (e.g. "Manage Contacts," "Manage Quotes," "Manage Meetings") with its own "grant all in this group" toggle switch and a real expand/collapse chevron, driven generically by an optional `group` field on `CAPABILITY_LABELS` (`packages/shared/src/schemas/permissions.ts`) — adding a new resource to this pattern requires zero new UI code, only new capability entries with the right `group` label. A resource's `delete_own`/`delete_others` pair is only added when a real delete route exists for it — several Jobs-family resources (Jobs, Milestones, Job Photos, Job Notes, Variation Orders) have no delete route at all today, so they were shipped with only `edit_own`/`edit_others` (and, where relevant, dedicated workflow-action capabilities), never speculative delete capabilities with nothing to gate. **Modules covered so far (rollout complete as of Phase 4 — every module in the app now uses this pattern)**: Contacts, Catalogue, Leads, Activities, Quotes, Meetings, Expenses, Expense Categories, Vendor Bills, Vendor Payments, Jobs, Milestones, Job Notes, Job Photos, Variation Orders, Invoices, Payments, Credit Notes. Invoices/Payments/Credit Notes were the final phase: `invoices.manage` (a single undifferentiated capability that had covered all three resources since Phase 2) is replaced by three independent own/others capability groups plus dedicated workflow capabilities for issue/void/send/send_reminder (Invoices), apply_credit/send_receipt (Payments), and issue (Credit Notes) — Payments has no update route at all, so `payments.edit_others` is reserved with nothing to gate yet, same shape as `vendor_payments.edit_others`. Extending this to a new module means: (1) confirm/add a stable ownership column, (2) add its 2–4 (or more, for workflow actions) capabilities to `CAPABILITIES`/`CAPABILITY_LABELS`/`DEFAULT_TEAM_GRANTS`, (3) move the ownership check into the service per existing examples, (4) write a hand-authored backfill migration for existing orgs, (5) update PRD §2.1's table + a new acceptance-highlight paragraph + CLAUDE.md's module list here, (6) add integration tests mirroring `contacts-catalog-ownership.integration.test.ts`, **(7) wire the web UI in the SAME phase** (see below) — do not defer UI wiring to a later catch-up pass, a shipped capability split with no UI reflection just shows buttons that 403 on click. Financial documents (Invoices, Payments, Credit Notes, Vendor Bills, etc.) additionally need care: `delete` there is already status-gated to draft-only (or similar) per CLAUDE.md's immutability rule, so the ownership check must run BEFORE that status check (a non-owner should get 403, not 400, on a non-draft record) — see `QuotesService.update`/`.delete`'s ordering for the established pattern. **If the resource is Field-reachable, there are two distinct mechanisms in `capability.util.ts`, both single-source-of-truth `ReadonlySet<Capability>` constants — pick the one matching the real semantics, don't default to one out of habit**: `FIELD_OWN_CAPABILITIES` (Expenses' submit/edit/delete, Job Photos'/Job Notes' create) is for a resource where Field genuinely only ever touches their OWN record — `requireOwnershipCapability`'s `fieldAccess: "own"` forwards `fieldAlwaysPasses` to `hasCapability` only on the `own` branch, never `others`. `FIELD_ALWAYS_CAPABILITIES` (Milestones' `edit_own`/`edit_others` together, for completion) is for the rarer case where the action was never an ownership question for Field to begin with regardless of who created the record — `fieldAccess: "always"` forwards it on BOTH branches. Both keep Field fixed/non-configurable (it never touches the Team privilege matrix); `getEffectiveCapabilities`'s Field branch must OR both sets together (`FIELD_OWN_CAPABILITIES.has(c) || FIELD_ALWAYS_CAPABILITIES.has(c)`) or the web UI will hide a button the service layer would actually allow — this exact bug shipped and was caught/fixed in the same change that introduced the second set, so double-check this line whenever either set gains a new capability. **Not every coarse capability that needed splitting was an own/others pair** — `dashboard.view` (a single grant covering the dashboard summary, receivables, payables, and job profitability together) was split into four independent read-visibility capabilities (`reports.view_dashboard_summary`, `reports.view_receivables`, `reports.view_payables`, `reports.view_job_profitability`), and `ledger.view` (previously defined in `CAPABILITIES` but wired to zero routes — pure dead weight) now gates `GET /reports/account-drilldown` for Staff, alongside Owner's pre-existing `@OrgRoles(["owner"])` bypass. This is the same "give each independently-useful grant its own toggle" principle as own/others, just without an ownership dimension — P&L/Balance Sheet/revenue-trend/tax-summary remain hard `@OrgRoles(["owner"])` with no capability escape hatch at all, since those were never gated by `dashboard.view` to begin with (see `reports.controller.ts`'s own class-level doc comment for the full breakdown of which routes are capability-gated vs. structurally Owner-only). **A third variant, for a true sub-resource with no creator of its own**: `contacts.manage_persons`/`contacts.manage_addresses` gate `ContactsService.update`'s `contactPersons`/`addresses` array fields — Contact Persons and Addresses have no `createdByUserId` column at all (they're whole-array-replaced as part of the parent contact's own `PUT`, not independently created/updated entities), so "own vs others" doesn't apply; each gets one plain capability, checked in ADDITION to (not instead of) the base `contacts.edit_own`/`edit_others` ownership check on the parent contact. Use this shape — one non-ownership capability per sub-resource, layered on top of the parent's own/others check — whenever a future resource has independently-toggleable write access but no per-row creator to split by. **A full audit of the whole rollout (prompted by "is everything related to privileges complete?") found one real gap after the "complete" declaration below**: `apps/web/src/app/(app)/contacts/leads-section.tsx` (the per-contact flat list, a separate component from the correctly-gated `/leads` kanban board) and `activities-section.tsx` (fixed the same day) had zero client-side capability gating despite the server enforcing `leads.edit_own`/`edit_others`/`activities.edit_own`/`edit_others` correctly all along — a reminder that "the server is correct" and "the UI reflects it" must be verified independently per component, not assumed from the resource being covered elsewhere. **Phase 5 (Mobile) added one new dedicated workflow-action capability to the already-covered Jobs module**: `jobs.assign` (owner/staff only) gates assigning/unassigning a job's crew via `POST/DELETE /jobs/:id/assignees` — separate from `jobs.edit_own`/`edit_others` since "who's on the crew" isn't an ownership question, and needed because it now decides which jobs a Field user's mobile home screen shows (`GET /jobs?assignedToMe=true`, backed by the new `job_assignments` join table). Web UI wired in the same change (job detail page's new "Crew" tab). See the 2026-08-30 CHANGELOG entry. **Phase 5 also added `quotes.accept_in_person`** (S-11.7 — a field/staff/owner user presents a quote on their own device and captures the customer's on-site acceptance) to the already-covered Quotes module: gates `POST /quotes/:id/accept-in-person`, a genuinely separate code path from the pre-existing unauthenticated public-link accept flow (`PublicQuotesService`, `@Public()`, no session, no actor) rather than that service with a session bolted on — the audit trail needs a real actor (`quotes.acceptedByUserId`/`acceptanceMethod: "in_person"`, new columns with no equivalent on the public path). Field always passes this capability unconditionally (added to `FIELD_ALWAYS_CAPABILITIES` in `capability.util.ts` — this is the entire point of S-11.7, never an ownership question); **the `hasCapability(..., fieldAlwaysPasses: true)` argument is easy to forget on a new `FIELD_ALWAYS_CAPABILITIES` entry and fails Field silently (403, not a crash) if omitted — this exact mistake was made and caught by this capability's own integration tests during Phase 5 development, matching the "double-check this line whenever either Field set gains a new capability" warning already documented above.** No mobile UI exists yet to wire (this endpoint is mobile-only and `apps/mobile` doesn't exist yet) — that wiring is deferred to whenever the mobile screens themselves are built, a deliberate, documented exception to the "wire the UI in the same phase" rule, not an oversight.

**Web UI wiring** (`apps/web/src/lib/capabilities-context.tsx`): `GET /org/members/me/capabilities` (backed by `getEffectiveCapabilities` in `capability.util.ts`) returns the current user's full effective capability set once per session, fetched by a `CapabilitiesProvider` mounted in `AppLayout`. Use `useCapability("resource.action")` for a plain check (e.g. gating a "+ New X" button), or `useCanEditOwnership(record.createdByUserId, { own, others })` for the own/others pattern on a specific record's Edit/Delete affordances — this hook's "own" definition must always match `requireOwnershipCapability`'s server-side one exactly. Both are UI convenience only (hide/disable an action the user can't use); the server still independently re-checks every mutating request regardless. One caveat: `useCanEditOwnership`/`useCapability` are React hooks and can't be called inside a non-component callback that's invoked once per item during a parent's render (e.g. a calendar's `renderEventPopover`) — in that shape, call `useCapabilities()` once at the top of the real component instead and re-derive the own/others branch manually per item (see `meetings-calendar.tsx`'s own comment for the worked example). Whenever a frontend module's hand-written TypeScript type (`types.ts`) mirrors a backend row shape, keep it in sync with new ownership columns — several were missing `createdByUserId` even after the backend had carried it for multiple phases, caught only when wiring the UI.
- **Deferred to v2, do not build**: multi-org (one owner account managing several separate organisations/instances) and cross-owner content ownership (restricting one Owner's access to another Owner's created records). See PRD §4.2 for why these are deferred and what would need to change to revisit them.
- **Invitation acceptance**: `POST /org/invitations` sends a real email (`sendInvitationEmail` wired in `auth.ts`, reusing `EmailService`) linking to `apps/web/src/app/accept-invite/[id]`, which calls Better Auth's own `getInvitation`/`acceptInvitation`/`rejectInvitation` client-side. Both of those **require an authenticated session matching the invited email** — Better Auth won't create an account inline, so an invitee without a session first goes through `/signup?inviteId=...&email=...` (email locked, pre-filled via the unauthenticated `GET /public/invitations/:id`) or `/login?next=/accept-invite/...`. There is still no automatic default-Team assignment on accept (the invited Staff user has zero Team memberships until an Owner assigns one from the Teams page) — if that's added later, it must be real application code run **after** `acceptInvitation` succeeds, **not** a `databaseHooks.member` hook: Better Auth 1.4.21's `databaseHooks` type (`BaseModelNames`) only covers `user`/`account`/`session`/`verification`, and the `organization` plugin's `member`/`invitation` writes aren't exposed through that hook surface (confirmed against `@better-auth/core`'s `type.d.mts` — re-check that type before re-attempting this, in case a future Better Auth upgrade changes it).
