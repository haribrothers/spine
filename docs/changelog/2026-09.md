### 2026-09-14 — `BottomSheet`: fixed content not filling a fixed-height (`snapPoints`) sheet's real width, root-caused to `matchContents` needing to be conditional; plus `SelectListField`'s Job Edit demo grown to 120 real options

- **User report**: `SelectListField`'s bottom sheet (search box + list) wasn't full-width — narrower than the sheet itself — and asked to test with a longer (100+ item) list.
- **Root cause, confirmed by reading `@expo/ui`'s own native source (`RNHostView.swift`)**: `BottomSheet`'s `children` were wrapped in `RNHostView matchContents` UNCONDITIONALLY. `matchContents` sizes the hosted SwiftUI wrapper to the RN child's own Yoga-measured INTRINSIC size, not the sheet's actual presented width — correct for a sheet with no `snapPoints` (genuine "size to content"), but wrong for a sheet like `SelectListField`'s with real, explicit `snapPoints` (a fixed-height sheet): there's no available width for the content's `100%`/`flex: 1` to resolve against at that boundary, so it collapsed to its narrowest intrinsic content instead of stretching.
- **Fix**: `matchContents` is now conditional — `true` only when `snapPoints` is NOT set (the genuine dynamic-sizing case, e.g. `BottomSheetDemo`'s plain `<BottomSheet>`), `false` whenever `snapPoints` IS set, which lets the content fill the sheet via `RNHostView`'s own non-`matchContents` fill branch instead. This exactly matches the rule `@expo/ui`'s OWN community bottom-sheet implementation already uses for this same fork (`fitToContents = enableDynamicSizing && (!snapPointsProp || snapPointsProp.length === 0)`) — not a guessed value.
- **`SelectListField`'s Job Edit demo (`CLIENT_OPTIONS`) grown from 10 hand-written entries to 120 generated ones** (20 name prefixes × 12 suffixes, truncated to 120), per explicit request to stress-test the search + `FlatList` at a realistic "org with a real contacts list" scale — real company-name-shaped strings (not "Client 1"..."Client 120") so the search filter is meaningfully exercisable. `ClientId` widened from a literal union to plain `string` since the list is now generated, not `as const`; `loadJob()`'s demo value updated to `"client-0-0"` ("Acme Contracting Ltd.," the first generated entry) to match.
- **New test coverage**: 2 new tests in `bottom-sheet.a11y.test.tsx` asserting `matchContents` is `true`/`false` for the no-`snapPoints`/with-`snapPoints` cases respectively.
- **Two follow-up bugs, found immediately while the user tested the 120-option list above, fixed in the same entry**: (1) each option row's height visibly shrank/felt cramped once the sheet's content correctly filled its real fixed height (rows were previously laid out against an accidentally-oversized intrinsic container, before the `matchContents` fix above) — fixed with a real fixed `OPTION_ROW_HEIGHT` (52px) `height` (not `minHeight` — see the next bug) on each row, replacing the previous `py-3`-only sizing, plus `numberOfLines={1}` on the label so a long name truncates instead of wrapping and growing past that fixed height. (2) reopening the sheet after picking a far-down option (e.g. the 50th of 120) always showed the list scrolled back to the TOP — fixed via `FlatList`'s `initialScrollIndex`, computed from the selected value's index in the (unfiltered) options list at the moment the sheet opens, plus `getItemLayout` (required for `initialScrollIndex` to work without first measuring every row) and an `onScrollToIndexFailed` fallback per RN's own documented guidance; `FlatList` is keyed on a bumped-per-open `openSessionId` since `BottomSheet` keeps its content mounted across `isPresented` toggles and `initialScrollIndex` only applies at mount.
- **A THIRD, more serious bug shipped in the same round and was caught by the user immediately after: the list stopped scrolling entirely.** First diagnosis (wrong, corrected before it stuck): `getItemLayout`'s fixed-length promise disagreeing with a `minHeight`-only row that could grow — real, and fixed (see bug (1)'s `height`/`numberOfLines` fix above), but NOT the actual cause of "not scrolling." **Second attempt — giving the `FlatList` `style={{ flex: 1 }}` — also did NOT fix it**, confirmed live. **Real root cause**: `BottomSheet`'s content sits inside `RNHostView`'s non-`matchContents` SwiftUI fill branch (`.frame(maxWidth: .infinity, maxHeight: .infinity)`), and the actual RN-side height for that subtree arrives via a size report-back through `ReportSizeToYogaNodeModifier`, not a normal Yoga layout pass a plain `flex: 1` child can reliably resolve against — the same "no resolvable dimension for a relative size" class of issue already documented at length in `full-width-button.tsx`'s history. **Fix**: the `FlatList` now gets a real, pre-computed PIXEL height (`useWindowDimensions().height * SHEET_HEIGHT_FRACTION - SHEET_CHROME_HEIGHT`, floored at 3 rows tall) instead of any flex/percentage sizing — `SHEET_HEIGHT_FRACTION` (0.75) is a single named constant shared with `BottomSheet`'s own `snapPoints` prop so the two can't drift apart. This sidesteps the native-bridge height-resolution question entirely rather than trying to make `flex`/`%` work through it.
- **Updated test coverage**: 2 new tests in `select-list-field.a11y.test.tsx` asserting `initialScrollIndex` is set to the selected option's real index (and `undefined` when nothing is selected). 124/124 `packages/ui-native` tests pass, 23/23 a11y coverage. Typecheck clean on both packages. NOTE: the scrolling fix itself (computed pixel height) was not yet confirmed on a real device at the time of this entry — the user's on-device testing loop for this fix is still in progress; re-verify against the live QA script section before considering this fully closed.

### 2026-09-14 — Job Edit (iOS): fixed the back-button discard-confirmation showing AFTER the screen closed, plus a follow-up double-alert bug found while fixing it

- **User report**: tapping the header back chevron with unsaved changes showed the discard-confirmation alert only AFTER the screen had already visibly closed, not before.
- **Root cause**: native-stack's default back button is a genuine `UIKit` control that starts its pop animation optimistically, before JS's `beforeRemove` listener gets a chance to call `event.preventDefault()`. The listener still correctly blocked the actual navigation-state change (the screen then slides back once the alert resolves), but that whole slide-away-then-back motion is exactly what was reported.
- **Fix**: the back chevron is now a custom `headerLeft` (a `Pressable` + `ChevronLeftIcon`, styled to match the native chevron via the render prop's own `tintColor`) that runs the SAME discard-check (`handleCancel`) synchronously, BEFORE any navigation starts — there's no native pop animation left to race against.
- **A second real bug surfaced immediately while testing the fix**: confirming "Discard" showed the SAME alert a second time right after. Cause: `handleCancel`'s `router.back()` call still triggers the still-armed `beforeRemove` listener, which re-checks `isDirty.current` — never cleared before the first `router.back()` call — and re-prompts for the exact same discard. Fixed by setting `isDirty.current = false` inside the discard callback, before calling `router.back()`, so the listener sees a clean form and lets the navigation through.
- Typecheck clean. Verified interactively by the user on a real iOS simulator (both the single-alert-before-close fix and the no-longer-doubled alert).

### 2026-09-13 — `FullWidthButton` moved off `@expo/ui`'s `Host`/`swift-ui Button` on iOS entirely: a real "no top spacing until first tap" bug, root-caused and fixed at the source, not worked around

- **User report**: on iOS, the Save button had no visible top spacing on first render — it sat flush against the card above it — but the correct gap appeared the instant the button was tapped, a visible "jump down."
- **Root-caused by reading `@expo/ui`'s own native source (`RNHostView.swift`)**: `Host`'s `matchContents` reports the true SwiftUI content size back to the RN shadow tree ASYNCHRONOUSLY, via `ReportSizeToYogaNodeModifier`'s `.onGeometryChange`/`.onChange(of: geometry.size)`, which only fires AFTER the first native layout pass. On mount, Yoga briefly lays out the `Host` (and its RN siblings, including the gap above it) using a stale/undersized height, which only visibly corrects once something forces an RN-side re-layout — exactly what a tap's state update does. A `setTimeout`-driven forced re-render shortly after mount was tried as a workaround first and did NOT reliably fix it (the native geometry callback's actual arrival time isn't bounded by a fixed JS timer) — abandoned in favor of removing the root cause instead.
- **A wrong intermediate diagnosis, corrected by the user before it shipped**: `job-edit-form.tsx`'s `ScrollView` `contentContainerClassName="gap-6 ..."` (a NativeWind flex `gap`) was suspected as the real cause and a `SECTION_GAP`/`marginTop` replacement was drafted — the user asked to revert this and pursue a custom-button fix in `FullWidthButton` instead, which is what shipped. That draft was fully reverted (`job-edit-form.tsx` has zero net changes in this entry).
- **The fix, iOS only**: `FullWidthButton` no longer uses `@expo/ui`'s `Host`/`swift-ui Button` on iOS at all — it's now a plain RN `Pressable` (`IOSFullWidthButton`) styled to visually approximate SwiftUI's `.borderedProminent`/`.bordered` look (solid/outlined pill, dimmed opacity while pressed, `controlSize` as a plain padding/font-size scale, `shape` as a real `borderRadius`). This eliminates the native-geometry round-trip the bug depends on entirely, rather than timing around it. Android is UNCHANGED — still the real `@expo/ui/jetpack-compose` `Button`/`OutlinedButton` with `fillMaxWidth()`, which was never affected (Android's `Host` box hugs its visible content tightly with no equivalent async gap).
- **A second real bug found while building the replacement**: `Pressable`'s own function-style `style={({ pressed }) => ({...})}` prop — standard, documented RN usage — rendered with NO styling applied at all on a real device (no background, no padding, no alignment, just bare unstyled text), confirmed via an on-device screenshot. Not fully root-caused, but the leading suspect is this app's `babel.config.js` routing every JSX element, including a bare `Pressable` with no `className`, through NativeWind's `nativewind/babel` interop wrapper — the first plain-RN-primitive `style` callback added to this package's `@expo/ui`-backed component set. Fixed by tracking pressed state with local `useState` and computing a plain (non-function) style object instead — confirmed working on a real device.
- **Tests**: `full-width-button.a11y.test.tsx` rewritten — iOS assertions now use real RNTL queries (`getByRole`, `getByText`) against actual RN primitives; Android tests (native-bridge-mock prop inspection) are unchanged. 120/120 `packages/ui-native` tests pass, 23/23 a11y coverage. Typecheck clean on both packages. Verified working on a real iOS simulator.

### 2026-09-13 — Investigated the iOS-vs-Android `FullWidthButton` spacing complaint down to its real root cause; the compensating fix itself was tried, confirmed broken on-device, and reverted

- **User pushback, correctly redirecting two earlier wrong diagnoses in a row**: round 1 claimed the iOS-vs-Android gap difference was "resolved as a side effect" of switching to `shape="rounded"` — wrong, the user re-reported the same issue with fresh screenshots. Round 2 (pixel-measuring the raw gap value, which came out equal on both platforms) suggested button HEIGHT was the real issue — also wrong, per explicit correction: "the problem is not the spacing between buttons, but the View in which the buttons are there and the Notes FormSection."
- **Root cause, correctly found this time** by wrapping a real on-device `Host` in a debug-colored `View` on both platforms: Android's `Host` box hugs its visible pill tightly on every edge (zero slack). iOS's `Host` box extends real, invisible space PAST the visible pill's bottom edge — SwiftUI reserving layout space to satisfy Apple's 44pt minimum tap-target height for `.borderedProminent` buttons, which `Host`'s `matchContents` correctly measures as part of the component's true layout box even though the pill itself paints shorter. `controlSize`/`buttonBorderShape` were both ruled out as levers (neither changed the slack) before concluding this was a fixed platform behavior, not a tunable modifier value.
- **The attempted fix (a hardcoded `marginBottom: -13` on the iOS `Host` wrapper) was ITSELF wrong, and is the actual subject of this entry** — not the diagnosis above, which held up. The `-13` value came from measuring a single vertical pixel column in one screenshot; real on-device testing (a fresh user screenshot, full-width scrolled view) showed this overshot badly enough to make Save and Cancel visibly OVERLAP — their rounded corners clipping into each other, worse than the original complaint. Root cause of the mismeasurement: a single sample column can miss real overlap entirely, since two rounded-rectangle shapes overlap far more visibly near their curved corners than at dead-center — exactly where the one column happened to land.
- **Final state: the margin compensation is fully reverted.** `FullWidthButton` now applies zero compensation around its `Host` on either platform — the raw, correct `Host` box (including iOS's invisible tap-target slack) is what callers space against, matching each platform's own accessibility-mandated control sizing rather than fighting it with a guessed constant. If this is revisited, any future compensation must be measured across the FULL button width in a real, complete (not cropped) on-device screenshot, with explicit before/after checks at both rounded corners specifically — not a single center column.
- 109/109 `packages/ui-native` tests pass (the regression test now asserts NO negative margin exists, replacing the one that asserted the broken fix's presence), 23/23 a11y coverage. Typecheck clean.
- **Process note**: three consecutive attempts at this one spacing complaint each corrected the previous mistake but introduced a new one, and the only reason the second mistake (the overlap) was caught was that the user kept testing the actual running app and reporting back with real screenshots rather than accepting a "fixed" claim backed only by narrow, self-reported pixel sampling. The standing lesson from this whole thread: a fix for a purely visual discrepancy is not verified until confirmed against a full, real on-device rendering — a single-column pixel sample or a cropped screenshot is not sufficient evidence, especially for anything involving curved/rounded shapes.

### 2026-09-13 — `Button`/`FullWidthButton` gain real `controlSize` and `shape` props; a genuine `@expo/ui` API-usage bug found and fixed along the way

- **User follow-up, two parts**: (1) the `gap-3` spacing between the in-content Save/Cancel buttons looked visually different on iOS vs. Android; (2) add `controlSize` (SwiftUI's real native control-size modifier) as a `Button`/`FullWidthButton` property, plus a `shape` prop (rounded/sharp/pill) for both.
- **`controlSize`**: added as a real prop on both `Button` and `FullWidthButton`, forwarding directly to SwiftUI's own `controlSize` modifier (`mini`/`small`/`regular`/`large`/`extraLarge`) on iOS. A genuine no-op on Android — Jetpack Compose's `@expo/ui` Button has no equivalent named-size concept (only a raw `contentPadding` prop taking exact dp values, a different API shape entirely) — same "real prop, iOS-only effect" pattern already established elsewhere in this package.
- **`shape` ("pill" | "rounded" | "sharp")**: this time actually works on both platforms, using a DIFFERENT, correct mechanism from the `clipShape` approach tried and abandoned earlier this session — SwiftUI's `buttonBorderShape` modifier genuinely changes what `.buttonStyle` PAINTS (unlike `clipShape`, which only crops after the fact). `Button` gets `shape` as iOS-only (its Android path has no `shape` prop reachable through the universal `@expo/ui` wrapper it uses); `FullWidthButton` gets it working on BOTH platforms, since it already uses `@expo/ui/jetpack-compose`'s direct `Button`/`OutlinedButton`, which has a real `shape` prop.
- **A genuine `@expo/ui` API-usage bug was found and fixed while wiring Android's `shape`**: passing `Shape.RoundedCorner(...)`/`Shape.Rectangle(...)`/even a bare `Shape.Pill` as JSX (`<Shape.RoundedCorner ... />`) silently broke the ENTIRE button — it stopped rendering completely, with no crash log and no JS error anywhere, reproduced consistently across a cold Metro restart and multiple relaunches. Root-caused by fetching Expo's own docs (`docs.expo.dev/versions/latest/sdk/ui/jetpack-compose/button`), which show `shape` constructed by CALLING the function directly (`shape={Shape.RoundedCorner({cornerRadii: {...}})}`), never as JSX. Fixed by calling `Shape.RoundedCorner({...})`/`Shape.Rectangle({...})` as plain functions instead of rendering them as elements — confirmed fixed on a real Android emulator, with a real visible rounded corner on both the filled Save and outlined Cancel buttons.

All 60 `packages/ui-native` tests pass, 17/17 components have a11y coverage (enforced by the existing `check-a11y-coverage.mjs` script).
- Verified end-to-end on both a real iOS simulator and a real Android emulator throughout — Phase 3's native chrome (tab bar, large-title header, scroll-edge blur/fade), Phase 4's mixed native+restyled screens, and Phase 5's full component/template navigation walk (including tapping into a dynamic `[jobId]`/`[slug]` route) were all confirmed live via screenshots, not just by reading the code. `pnpm typecheck` is clean across `packages/ui-native`, `apps/showcase-native`, `apps/design-system-native`, and `apps/mobile`.
