## What Spine is

Spine is a self-hosted business management app for small service/project businesses (construction, fabrication, contractors, design studios). It follows the workflow **enquiry → quote → job → invoice → payment → books**, where double-entry accounting is derived automatically from business events rather than entered directly by users. Read `docs/spine-prd.md` in full before making architectural decisions — it is the single source of truth for scope, data model, and rationale.

## Core architectural rules (non-negotiable per PRD §6, §10.4)

These constraints protect financial correctness and should govern any implementation work in this repo:

- **Ledger is derived, never authored.** Every business event (invoice issued, payment received, etc.) flows through a domain service → a posting rule → a balanced journal entry. Users never type a journal entry. Posting rules live in one module (see §7.2 for the full debit/credit table).
- **Journal entries are immutable.** Corrections are reversing entries, never edits. A DB constraint enforces debits == credits per entry, in the same transaction as the business document it originates from.
- **Money is integer minor units (`bigint`) + currency code.** No floats. Rounding happens once, at line level, half-up. Tax is computed per line, not per document.
- **Documents snapshot their data.** Catalogue price/tax changes must never alter existing quotes/invoices — issued documents store a snapshot at time of issue.
- **Document numbers are gapless and permanent.** Allocated inside the issuing transaction via a row lock on a sequence table; drafts have no number; numbers never change once assigned.
- **Issued financial documents are never edited or deleted.** Only voided (with reversing entry) or credited.
- **Server-side authorization on every endpoint** — never trust a client-supplied role.
- **Idempotency keys on all mutating endpoints** (critical for the mobile offline outbox pattern, §6.6).

## Key design decisions to preserve when implementing

- **Job costing without a parallel subsystem**: journal lines carry optional `contact_id` and `job_id`. AR aging and job profitability come from filtering the ledger, not from separate calculations — don't build a shadow costing system.
- **Retention** posts to a dedicated `Retention Receivable` account, distinct from AR, so aging reports aren't distorted by held retention.
- **Quote versioning** uses `parent_quote_id`; revising a sent quote creates a new version and supersedes the old one rather than mutating it.
- **Mobile offline model is intentionally partial** (§6.6): read-only cache (SQLite) for lists, write via an outbox queue with idempotency keys for photos/expenses/milestone updates. No offline creation of financial documents (quotes/invoices) — those require connectivity.
- **`@spine/ui` is built once in Phase 0**, not incrementally per feature — theme tokens as CSS custom properties, dark/light mode, docs in `apps/design-system` (a custom Next.js docs app, not Storybook), WCAG 2.1 AA per component, so later phases consume a finished library instead of inventing components mid-feature.
- **Every `@spine/ui` component change ships with its `apps/design-system` doc page in the same change.** Adding a new component or updating an existing one's API/behavior always includes creating or updating its page under `apps/design-system/src/app/components/<name>/page.tsx` (and its `apps/design-system/src/lib/nav.ts` entry for new components) — the design-system app is the living spec for the library, not an afterthought, and must never drift behind `packages/ui`'s actual exports.
- **`packages/ui-native` has its own equivalent doc app: `apps/design-system-native`** (an Expo/React Navigation app, not a web/Next.js one — `ui-native` components render RN primitives via NativeWind `className`, which don't render in a browser DOM, so they can't be shown in the existing web `apps/design-system`). Same rule as web: every `packages/ui-native` component change ships with its doc screen under `apps/design-system-native/app/components/<name>.tsx`, using the shared doc-page primitives in `src/components/doc-page.tsx` (`DocTitle`/`DocLead`/`DocSection`/`DocSubsection`/`FeatureList`/`ApiTable`) plus `ComponentPreview`/`CodeBlock` for live previews and code snippets — the same Title/Lead/Preview/Features/Anatomy/API Reference/Examples/Accessibility structure `apps/design-system`'s own component pages use, RN-rendered instead of DOM. Register the new screen in **two** places in the same change: `src/lib/component-registry.ts` (nav metadata) and `src/lib/component-screens.ts` (the slug→screen map both shells render from). Run it via `pnpm dev:ui-native` (or `--ios`/`--android`/`--web` variants), which launches Expo like `apps/mobile` does.
- **`apps/design-system-native` renders one of two shells based on viewport width, not platform** (`src/lib/use-is-desktop-layout.ts`, a 768px `useWindowDimensions` breakpoint) — deliberately width-based rather than `Platform.OS`-based, so a narrowed desktop browser window gets the same mobile layout a phone does, matching how a responsive web page behaves. **Desktop (≥768px)**: `src/components/desktop-shell.tsx` — a persistent top bar (`desktop-top-bar.tsx`) + sidebar (`desktop-sidebar.tsx`) + content pane, mirroring `apps/design-system`'s `DocsShell`/`Sidebar`/`TopBar` look. Selection there is local `useState` in `DesktopShell`, not React Navigation — a single-pane desktop layout has no page transition to model, so there's no navigator involved on that branch at all. **Mobile (<768px)**: `src/navigation/root-navigator.tsx`'s existing stack (Home list → push Component detail) — this is the only place React Navigation is used. Both shells render the exact same per-component screen component from `component-screens.ts`; only the surrounding chrome differs.
- **`DesktopSidebar`'s width is a plain inline `style`, not a NativeWind `w-56`/`shrink-0` className** — confirmed by inspecting a real `expo export --platform web` bundle that those classNames were silently dropped from the compiled CSS on `ScrollView` specifically, causing the sidebar to stretch full-width instead of staying at 224px. Don't "clean this up" back into a className if you touch this file; the inline style is the fix, not a stopgap.
- **`@expo/vector-icons`** (bundled with every Expo SDK, added as an explicit direct dependency since pnpm doesn't hoist it automatically) is the icon library for both `apps/design-system-native`'s theme toggle (`theme-toggle.tsx`, `Feather` icons: **sun = light, moon = dark, monitor = system** — three states, not web's two, since `ui-native`'s `ThemeProvider` is deliberately three-state; the icon shows the CURRENT preference, not the state pressing it switches to — an earlier version had this scrambled (`light: "moon"`, `dark: "monitor"`, `system: "sun"`), which made a correctly-working toggle look broken because the icon didn't match the preference a user would expect, fixed 2026-08-30) and its search button (`desktop-top-bar.tsx`/`root-navigator.tsx`'s `SearchButton`). `apps/design-system`'s `SearchPalette` uses `cmdk`, which is DOM-only (web-specific portal/keyboard behavior) — `search-palette.tsx` re-implements the same "type to filter, press to select" UX with RN's `Modal`/`TextInput`/`FlatList` instead of porting the library, filtering the same `component-registry.ts` list both shells already share. Cmd/Ctrl+K global capture is wired via a `Platform.OS === "web"`-gated `document.addEventListener` — native has no hardware-keyboard-driven command-palette convention, so native users open it via the search button only.
- **`packages/ui-native` components must run their final className through `cn` (`src/lib/cn.ts`, clsx + tailwind-merge), never `cva`'s raw output or a plain string/array concatenation, whenever a component composes two independently-conditioned class sets that can touch the same CSS property** (e.g. a `variant` axis and a `disabled` axis both setting a background/text color). `packages/ui`'s Button resolves this on web via Tailwind's `disabled:` pseudo-class, a real specificity bump that wins regardless of source order — NativeWind has no equivalent pseudo-class for `Pressable`, so two same-specificity conflicting utility classes (e.g. a variant's `bg-primary` vs. a disabled override's `bg-transparent`) resolve by Tailwind's build-time CSS-discovery order, NOT by which class appears later in the string. This silently broke Button's disabled-state text (shipped invisible: `<Button disabled>` with the default `primary` variant rendered white text on a transparent background) until fixed by wrapping both `buttonVariants(...)` and `textVariants(...)` calls in `cn(...)`, which deterministically drops the earlier conflicting class. `button.a11y.test.tsx`'s regression test asserts every variant's disabled text className contains `text-on-surface-muted` and never the variant's own text color — follow this same pattern (`cn`-wrap + a regression test asserting the losing class is actually absent, not just that the winning class is present) for any future `ui-native` component with a similar two-independent-conditions composition.
- **Button's `loading` prop has no web `packages/ui` equivalent to mirror — it's a `ui-native`-only addition, and its own follow-on bug is a reminder to re-derive EVERY visual consequence of a state change, not just the one first reported.** `loading` sets `isDisabled` internally, which (correctly, per the fix above) makes the button's background the disabled look (`bg-transparent`) regardless of variant — but the `ActivityIndicator`'s `color` prop was still hardcoded to `#FFFFFF` for `primary`/`danger` from before the disabled-text fix landed, so the spinner was invisible against its own now-transparent background (a second real shipped bug, found right after the first). Fixed by resolving the spinner's color from `nativewind`'s `useColorScheme()` against `lightColors.onSurfaceMuted`/`darkColors.onSurfaceMuted` — the same color the disabled label text uses — instead of a variant-conditioned hardcoded hex. `button.a11y.test.tsx` has a matching regression test (`UNSAFE_getByType(ActivityIndicator)`, asserting `color` is never `#FFFFFF`), confirmed to fail without the fix. Lesson for future `ui-native` work: when a prop changes visual state via a shared flag like `isDisabled`, audit every other prop/element whose value was computed assuming the OLD state (a hardcoded color keyed off `variant` alone, here) — a partial fix that addresses only the originally-reported symptom can leave a sibling bug from the very same root cause.
- **`packages/ui-native`'s dark-mode colors are NOT a `{ DEFAULT, dark }` color-object shape in any `tailwind.config.js` — that shape silently does nothing.** Tailwind's color flattening has no special meaning for a `dark` sub-key (`DEFAULT`/`50`/`100`/.../`900` are the only recognized shapes), so a color defined that way always compiles to ONE fixed light-mode value — confirmed live: with that shape, a real `expo export --platform web` bundle's compiled CSS had ZERO `.dark` selectors anywhere, meaning the light/dark/system toggle changed the `colorScheme` state correctly (that mechanism, `nativewind`'s `colorScheme.set(...)` via `theme-provider.tsx`, was never broken) but nothing on screen ever visibly changed — this shipped and went unnoticed in `apps/mobile` for multiple phases simply because `apps/mobile` had no toggle UI to exercise it until `apps/design-system-native` added one and a user reported it. **The real, working mechanism**: `apps/mobile/tailwind.config.js` and `apps/design-system-native/tailwind.config.js` each register every themed color TWICE via local `flatColors`/`flatDarkColors` helpers — once under its plain name from `lightColors`, once under `<name>-dark` from `darkColors` (e.g. `surface` and `surface-dark`) — and every themed utility class in every component/screen must be written with an explicit paired `dark:` variant of the same base name (`className="bg-surface dark:bg-surface-dark"`, `"text-on-surface-muted dark:text-on-surface-muted-dark"`, etc.), including on `active:`-prefixed classes (`active:bg-surface-sunken active:dark:bg-surface-sunken-dark` — verified this exact stacked-variant ordering compiles to a real rule, not `dark:active:`). This produces genuine NativeWind-compiled `.dark`-scoped CSS rules the runtime toggle can actually switch to, exactly like a standard Tailwind project's own `dark:` classes — verified directly by inspecting compiled CSS output (`.dark\:bg-surface-dark:is(.dark *){...}` present with the correct dark color value) both before and after the full fix. **A hardcoded raw color prop is a separate, easy-to-miss gap this pattern doesn't cover**: `TextField`'s `placeholderTextColor="#726C5A"` is a native RN prop, not a NativeWind className, so it stays the light-mode `onSurfaceMuted` value in dark mode too — same class of gap as Button's `ActivityIndicator` `color` prop (fixed above), not yet fixed here; resolve it the same way (via `useColorScheme()`) if/when it's reported. **When adding any new `packages/ui-native` component or screen, or any new consumer of an existing one, every themed `bg-*`/`text-*`/`border-*` class must get its `dark:*-dark` pair in the same change** — there is no lint/build check that catches a missing pair (unlike the a11y-coverage script below), so this is a discipline rule, not a machine-enforced one; a bare `bg-surface` with no `dark:` pair is not obviously broken by inspection alone (it just always looks like light mode), which is exactly how this shipped unnoticed the first time.
- **`react-native-css-interop@0.2.6`'s web `colorScheme.set("system")` has a real upstream bug: it NEVER actually checks the OS/browser's `prefers-color-scheme` — it unconditionally removes the `.dark` class**, confirmed by reading its own `dist/runtime/web/color-scheme.js` (`set()`'s only special case is `value === "dark"`; every other value, including `"system"`, falls into an unconditional `classList.remove(...)`) and reproduced live with a headless-browser test forcing `prefers-color-scheme: dark` — `.set("system")` still left the page in light mode. **Fix, in `packages/ui-native/src/theme/theme-provider.tsx`**: a web-only `applyPreference` helper that, when `preference === "system"` on `Platform.OS === "web"`, resolves `window.matchMedia("(prefers-color-scheme: dark)")` itself and calls `.set("dark" | "light")` directly — NEVER `.set("system")` on web — plus a live `matchMedia` `change` listener (tracked in a ref and cleaned up on every preference change, not just on unmount, to avoid leaking one listener per toggle click) so an OS-level theme switch while still on "system" is picked up without a reload. Native is unaffected (its `Appearance`-based path doesn't share this bug) and still calls `.set("system")` directly. **The boot-time default matters just as much as the toggle**: the effective preference (`stored ?? "system"`) must be explicitly (re-)applied via this same helper even when `storage.getPreference()` resolves `null` (a fresh session with no saved preference) — the original code only called `nativeWindColorScheme.set(...)` when a STORED value existed, silently leaving NativeWind's own boot-time default (which hits the exact same "system" bug) in effect for every first-time visitor; this was caught only by testing the fresh-session case specifically, after the explicit-toggle case already looked fixed. Verified end-to-end with headless-browser tests covering all three cases: fresh boot with browser set dark, explicit cycle back to "system" with browser set light, and the same cycle with browser set dark — plus a live OS-preference-change simulation while parked on "system".
- **`apps/design-system-native`'s theme preference persists across reloads** (`src/lib/theme-storage.ts`'s `persistentThemeStorage`) — an earlier version used an in-memory-only `ThemeStorage` (reset on every reload), a deliberate initial scoping choice that shipped as a real reported friction point once the toggle was actually used day to day. `expo-secure-store` (what `apps/mobile`'s own `theme-storage.ts` uses) has NO web implementation at all — its `.web.ts` is an empty stub, confirmed by reading the installed package — so this storage branches on `Platform.OS`: `localStorage` on web (a theme preference isn't remotely sensitive, so a bare synchronous browser API is fine; no need for SecureStore's native-only encryption story), `expo-secure-store` on native for consistency with `apps/mobile`'s choice. Verified persistence live with a headless-browser reload test, not just by reading the code.
- **React Navigation's own chrome (native-stack headers, bottom-tab bars, drawer chrome, etc.) is NOT NativeWind-styled and ignores `dark:` classes entirely** — it's rendered by React Navigation itself, outside any app's className-based component tree, and only reacts to the `theme` prop passed to `NavigationContainer` (`@react-navigation/native`'s own `DefaultTheme`/`DarkTheme`, a generic blue/gray palette unrelated to this design system's tokens). This shipped as a real, user-reported bug in `apps/design-system-native`: a dark-mode screenshot showed a correctly-dark body under a still-light header, because `RootNavigator` never passed a `theme` prop at all. Fixed via **`packages/ui-native/src/navigation/navigation-theme.ts`'s `spineLightNavigationTheme`/`spineDarkNavigationTheme`** (built from `lightColors`/`darkColors`, not React Navigation's defaults, and exported from the shared package — via `@spine/ui-native/navigation`, a dedicated subpath export like `./tokens` — rather than duplicated per app, since it's a pure function of the shared color tokens with zero app-specific logic), selected via `useTheme().resolvedMode` and passed to `NavigationContainer`'s `theme` prop. `@react-navigation/native` is an **optional peer dependency** of `packages/ui-native` (not a hard dependency) so apps that don't use React Navigation aren't forced to install it. **`apps/mobile`'s bottom-tab bar was proactively fixed the same way** even before it had a visible dark-mode toggle UI to expose the bug — the exact same gap (`NavigationContainer` with no `theme` prop) was present there too, just latent, and the whole point of finding this bug once is not shipping it twice. **Any future native-stack/tab/drawer screen in either app must pass this same `theme` prop** — pairing `dark:` classes on an app's own View/Text components does nothing for chrome React Navigation renders itself; that chrome needs a `theme` prop (or per-screen `headerStyle`/`headerTintColor` options for one-off overrides), never NativeWind classes.
- **Every `@spine/ui` component ships with an automated accessibility regression test in the same change.** A new component at `packages/ui/src/components/<name>.tsx` requires a matching `packages/ui/src/components/<name>.a11y.test.tsx` (axe-core via `expectNoA11yViolations` from `packages/ui/src/test/a11y.ts`, run under vitest+jsdom, scoped to WCAG 2.1 A+AA rule tags), rendering the component in a representative default/open state (Radix overlays: actually opened via `open`/`defaultOpen` and asserted against `document.body`, since Radix portals content there) plus any states that meaningfully change its accessible semantics (variants, disabled/invalid, checked/unchecked). This is enforced, not just documented: `packages/ui/scripts/check-a11y-coverage.mjs` runs as part of `pnpm --filter @spine/ui test` and fails the build if any component lacks a matching test file — the same "ships together" pattern as the doc-page rule above, but machine-checked rather than relying on the same discipline. Added 2026-08-29 as the recommended follow-up from that day's WCAG 2.1 AA audit-and-fix pass, so future component changes get a regression net instead of a fresh manual audit each time.
- **First-run onboarding is not a gate.** The app must be fully usable if the wizard is skipped; onboarding settings (industry template, tax, numbering, etc.) must remain editable later from Settings.
- **Onboarding never includes database/infra setup.** Provisioning Postgres and its credentials happens before the app ever serves a page — via `scripts/install.sh` and `.env` (`DATABASE_URL`), not an in-app step. The wizard begins only after sign-up (first user on a fresh instance becomes the **Primary Owner** automatically — see the permission model section below), and its step order is fixed: business profile → industry template → currency/locale/financial year → tax rates → numbering prefixes → chart-of-accounts confirmation → team invite. "Load demo data" is an alternative/supplement offered at step 1, not a separate flow. Every step must remain skippable and re-editable from Settings (§S-12.10), per the rule above.
- **Profile & Preferences is not the same surface as org Settings.** Every user, regardless of role, gets a personal page (name, email, password, avatar, preferences) reachable from the user menu — separate from the Owner-only organisation Settings dialog and separate from the Users/Teams/Permissions area. Don't fold personal account editing into either of those.
- **Graceful degradation**: if SMTP is down, documents still issue and email queues for retry; if object storage is down, the app runs read-only for attachments rather than failing globally. The app must boot with only 3 required env vars (`DATABASE_URL`, `AUTH_SECRET`, `APP_URL`).

## Permission model (PRD §2.1) — read before touching auth, roles, or any endpoint's authorization check

- **Roles**: `owner`, `staff`, `field` on `memberships`, plus the external customer link role. Owner and Field are fixed, non-configurable. Staff is subdivided by **Teams** — an org creates named Teams (`teams`), each with a configurable privilege matrix (`team_privileges`, one boolean row per Team per capability). A Staff user can belong to multiple Teams; effective access to a capability is the union across their Teams (most-permissive-wins, no explicit-deny in v1).
- **Primary Owner**: the first signup on a fresh instance. Exactly one per org, enforced by a partial unique index on `memberships.is_primary_owner`, not application logic alone. Cannot be demoted or removed by anyone but themselves, and only via an explicit transfer action — never a side effect of role editing. Signup is single-use: every account after the first is created by invite, never public registration.
- **Multiple Owners**: any Owner can promote a Staff user to Owner. All Owners have equal, unrestricted access — there is no per-owner content ownership or restriction in v1 (see "Deferred to v2" below). **Owner is never granted at invite time** — `POST /org/invitations` rejects `role: "owner"` outright (Better Auth's own `createInvitation` would otherwise allow it); the only path to Owner is `PUT /org/members/:id/promote` on an existing Staff member who has already accepted an invite and joined.
- **Field stays fixed on purpose**: never make Field Team-configurable — it exists specifically so an owner can't accidentally widen a mobile user's access to financial data (protects the "mobile hides all financial reports" rule, PRD §S-11.8).
- **"Manage users, teams, permissions, org settings, tax rules" is Owner-only, not Team-configurable, ever** — it's the one capability that could otherwise grant itself broader access.
- **Single source of truth**: the capability list the permissions UI renders and the list the API enforces per-endpoint must be the same list. If you add a new capability to the privilege matrix UI without a matching server-side check (or vice versa), that's a bug, not a follow-up.
- **Nav placement**: Users/Teams/Permissions management lives in its own top-level, Owner-only sidebar section with real routes — not inside the org Settings dialog. Settings stays for organisation configuration (branding, tax, numbering, business profile, etc.). See PRD §9 FEAT-10 S-10.18.
- **Whenever a new feature changes who-can-do-what** — adds a capability, a resource, or an action that should be gated — update the privilege matrix (the Team-configurable capability list) and this section of CLAUDE.md in the same change. A feature that's gated only in the UI, or only in one layer, is incomplete.
- **`meetings.manage`** (Team-configurable) gates create/update/delete of meetings, replacing an earlier piggyback on `contacts.manage`. It does **not** control who can *see* a given meeting — meeting read-access is a separate, capability-independent check: a meeting's own `visibility` (`private`|`org`) plus its invite list (`meeting_attendees`) decides who can read it via `GET /meetings`/`GET /meetings/:id`, enforced in `MeetingsService` regardless of `meetings.manage`. Owners always see every meeting (private or org) per the blanket-access rule above; Staff/Field only see `org`-visibility meetings or `private` ones they organize or are invited to. Responding to your own invite (`POST /meetings/:id/respond`) requires no capability at all — it's self-service, gated only by having an attendee row. When adding any future meetings-adjacent capability, keep this "manage ≠ can-read" split — don't let a management grant widen read access.
- **Own/others ownership-based capability split — the general pattern, being extended module by module** (PRD §9, e.g. FEAT-01 S-01.15/S-01.16/S-01.17, FEAT-02 S-02.5, FEAT-03 S-03.13). Read is unconditional (no capability gate at all on `GET` routes); write/delete are split into a **four-capability group per resource** — `<resource>.edit_own`/`edit_others`/`delete_own`/`delete_others` — enforced in the SERVICE layer (not the route guard, since ownership depends on the record's `createdByUserId`/equivalent, which isn't known until the record is loaded) via `requireOwnershipCapability` (`apps/api/src/auth/capability.util.ts`), called right after the existing read-before-write lookup in `update`/`archive`/`restore`/`delete`. `<resource>.edit_own` also gates **create** — a Team with neither `edit_own` nor `edit_others` cannot create new records of that type at all, only view existing ones. A Team's grants for one resource are completely independent of every other resource's grants (`contacts.edit_others` implies nothing about `catalog.edit_others`, `quotes.edit_others`, etc.). "Own" means a stable creator/organizer signal, set once and never reassigned — deliberately distinct from a resource's own reassignable people-fields when one exists (`leads.ownerUserId` pipeline rep, `activities.assignedToUserId` delegate, `meetings.organizerUserId` — wait, meetings use organizer AS the ownership signal since there's no separate creator field; the point is: whichever field is chosen as "own" for a resource, it must never silently change just because the record gets reassigned to someone else). A resource with no `createdByUserId`-equivalent column at all (e.g. meetings) uses the closest stable "this person owns/organizes it" field instead — documented per-module. A `null`/unset owner (legacy pre-migration rows) is treated as unowned: only `_others` can touch it, never `_own`, even for the user who might otherwise seem to have created it. **Workflow actions that aren't edits** (send/revise a quote, approve/reject an expense, issue/void an invoice, etc.) get their OWN dedicated capability rather than being folded into `edit_own`/`edit_others` — "can I edit my own draft" and "can I send/approve/void" are different questions an Owner may want to grant separately, and conflating them (e.g. treating an approver's action as if it were "editing the submitter's own record") misrepresents the actual relationship. The seeded "General Staff" default Team grants every one of these capabilities `true` on introduction (preserving pre-split full-access behavior for every existing org via a hand-authored backfill migration, same pattern each time — see `apps/api/drizzle/0036`–`0040` for worked examples) — Owners narrow per-Team afterward if they want a more restrictive split. The Team privilege-matrix UI (`team-detail-view.tsx`) renders each resource's capabilities as a collapsible group (e.g. "Manage Contacts," "Manage Quotes," "Manage Meetings") with its own "grant all in this group" toggle switch and a real expand/collapse chevron, driven generically by an optional `group` field on `CAPABILITY_LABELS` (`packages/shared/src/schemas/permissions.ts`) — adding a new resource to this pattern requires zero new UI code, only new capability entries with the right `group` label. A resource's `delete_own`/`delete_others` pair is only added when a real delete route exists for it — several Jobs-family resources (Jobs, Milestones, Job Photos, Job Notes, Variation Orders) have no delete route at all today, so they were shipped with only `edit_own`/`edit_others` (and, where relevant, dedicated workflow-action capabilities), never speculative delete capabilities with nothing to gate. **Modules covered so far (rollout complete as of Phase 4 — every module in the app now uses this pattern)**: Contacts, Catalogue, Leads, Activities, Quotes, Meetings, Expenses, Expense Categories, Vendor Bills, Vendor Payments, Jobs, Milestones, Job Notes, Job Photos, Variation Orders, Invoices, Payments, Credit Notes. Invoices/Payments/Credit Notes were the final phase: `invoices.manage` (a single undifferentiated capability that had covered all three resources since Phase 2) is replaced by three independent own/others capability groups plus dedicated workflow capabilities for issue/void/send/send_reminder (Invoices), apply_credit/send_receipt (Payments), and issue (Credit Notes) — Payments has no update route at all, so `payments.edit_others` is reserved with nothing to gate yet, same shape as `vendor_payments.edit_others`. Extending this to a new module means: (1) confirm/add a stable ownership column, (2) add its 2–4 (or more, for workflow actions) capabilities to `CAPABILITIES`/`CAPABILITY_LABELS`/`DEFAULT_TEAM_GRANTS`, (3) move the ownership check into the service per existing examples, (4) write a hand-authored backfill migration for existing orgs, (5) update PRD §2.1's table + a new acceptance-highlight paragraph + CLAUDE.md's module list here, (6) add integration tests mirroring `contacts-catalog-ownership.integration.test.ts`, **(7) wire the web UI in the SAME phase** (see below) — do not defer UI wiring to a later catch-up pass, a shipped capability split with no UI reflection just shows buttons that 403 on click. Financial documents (Invoices, Payments, Credit Notes, Vendor Bills, etc.) additionally need care: `delete` there is already status-gated to draft-only (or similar) per CLAUDE.md's immutability rule, so the ownership check must run BEFORE that status check (a non-owner should get 403, not 400, on a non-draft record) — see `QuotesService.update`/`.delete`'s ordering for the established pattern. **If the resource is Field-reachable, there are two distinct mechanisms in `capability.util.ts`, both single-source-of-truth `ReadonlySet<Capability>` constants — pick the one matching the real semantics, don't default to one out of habit**: `FIELD_OWN_CAPABILITIES` (Expenses' submit/edit/delete, Job Photos'/Job Notes' create) is for a resource where Field genuinely only ever touches their OWN record — `requireOwnershipCapability`'s `fieldAccess: "own"` forwards `fieldAlwaysPasses` to `hasCapability` only on the `own` branch, never `others`. `FIELD_ALWAYS_CAPABILITIES` (Milestones' `edit_own`/`edit_others` together, for completion) is for the rarer case where the action was never an ownership question for Field to begin with regardless of who created the record — `fieldAccess: "always"` forwards it on BOTH branches. Both keep Field fixed/non-configurable (it never touches the Team privilege matrix); `getEffectiveCapabilities`'s Field branch must OR both sets together (`FIELD_OWN_CAPABILITIES.has(c) || FIELD_ALWAYS_CAPABILITIES.has(c)`) or the web UI will hide a button the service layer would actually allow — this exact bug shipped and was caught/fixed in the same change that introduced the second set, so double-check this line whenever either set gains a new capability. **Not every coarse capability that needed splitting was an own/others pair** — `dashboard.view` (a single grant covering the dashboard summary, receivables, payables, and job profitability together) was split into four independent read-visibility capabilities (`reports.view_dashboard_summary`, `reports.view_receivables`, `reports.view_payables`, `reports.view_job_profitability`), and `ledger.view` (previously defined in `CAPABILITIES` but wired to zero routes — pure dead weight) now gates `GET /reports/account-drilldown` for Staff, alongside Owner's pre-existing `@OrgRoles(["owner"])` bypass. This is the same "give each independently-useful grant its own toggle" principle as own/others, just without an ownership dimension — P&L/Balance Sheet/revenue-trend/tax-summary remain hard `@OrgRoles(["owner"])` with no capability escape hatch at all, since those were never gated by `dashboard.view` to begin with (see `reports.controller.ts`'s own class-level doc comment for the full breakdown of which routes are capability-gated vs. structurally Owner-only). **A third variant, for a true sub-resource with no creator of its own**: `contacts.manage_persons`/`contacts.manage_addresses` gate `ContactsService.update`'s `contactPersons`/`addresses` array fields — Contact Persons and Addresses have no `createdByUserId` column at all (they're whole-array-replaced as part of the parent contact's own `PUT`, not independently created/updated entities), so "own vs others" doesn't apply; each gets one plain capability, checked in ADDITION to (not instead of) the base `contacts.edit_own`/`edit_others` ownership check on the parent contact. Use this shape — one non-ownership capability per sub-resource, layered on top of the parent's own/others check — whenever a future resource has independently-toggleable write access but no per-row creator to split by. **A full audit of the whole rollout (prompted by "is everything related to privileges complete?") found one real gap after the "complete" declaration below**: `apps/web/src/app/(app)/contacts/leads-section.tsx` (the per-contact flat list, a separate component from the correctly-gated `/leads` kanban board) and `activities-section.tsx` (fixed the same day) had zero client-side capability gating despite the server enforcing `leads.edit_own`/`edit_others`/`activities.edit_own`/`edit_others` correctly all along — a reminder that "the server is correct" and "the UI reflects it" must be verified independently per component, not assumed from the resource being covered elsewhere. **Phase 5 (Mobile) added one new dedicated workflow-action capability to the already-covered Jobs module**: `jobs.assign` (owner/staff only) gates assigning/unassigning a job's crew via `POST/DELETE /jobs/:id/assignees` — separate from `jobs.edit_own`/`edit_others` since "who's on the crew" isn't an ownership question, and needed because it now decides which jobs a Field user's mobile home screen shows (`GET /jobs?assignedToMe=true`, backed by the new `job_assignments` join table). Web UI wired in the same change (job detail page's new "Crew" tab). See the 2026-08-30 CHANGELOG entry. **Phase 5 also added `quotes.accept_in_person`** (S-11.7 — a field/staff/owner user presents a quote on their own device and captures the customer's on-site acceptance) to the already-covered Quotes module: gates `POST /quotes/:id/accept-in-person`, a genuinely separate code path from the pre-existing unauthenticated public-link accept flow (`PublicQuotesService`, `@Public()`, no session, no actor) rather than that service with a session bolted on — the audit trail needs a real actor (`quotes.acceptedByUserId`/`acceptanceMethod: "in_person"`, new columns with no equivalent on the public path). Field always passes this capability unconditionally (added to `FIELD_ALWAYS_CAPABILITIES` in `capability.util.ts` — this is the entire point of S-11.7, never an ownership question); **the `hasCapability(..., fieldAlwaysPasses: true)` argument is easy to forget on a new `FIELD_ALWAYS_CAPABILITIES` entry and fails Field silently (403, not a crash) if omitted — this exact mistake was made and caught by this capability's own integration tests during Phase 5 development, matching the "double-check this line whenever either Field set gains a new capability" warning already documented above.** No mobile UI exists yet to wire (this endpoint is mobile-only and `apps/mobile` doesn't exist yet) — that wiring is deferred to whenever the mobile screens themselves are built, a deliberate, documented exception to the "wire the UI in the same phase" rule, not an oversight.

**Web UI wiring** (`apps/web/src/lib/capabilities-context.tsx`): `GET /org/members/me/capabilities` (backed by `getEffectiveCapabilities` in `capability.util.ts`) returns the current user's full effective capability set once per session, fetched by a `CapabilitiesProvider` mounted in `AppLayout`. Use `useCapability("resource.action")` for a plain check (e.g. gating a "+ New X" button), or `useCanEditOwnership(record.createdByUserId, { own, others })` for the own/others pattern on a specific record's Edit/Delete affordances — this hook's "own" definition must always match `requireOwnershipCapability`'s server-side one exactly. Both are UI convenience only (hide/disable an action the user can't use); the server still independently re-checks every mutating request regardless. One caveat: `useCanEditOwnership`/`useCapability` are React hooks and can't be called inside a non-component callback that's invoked once per item during a parent's render (e.g. a calendar's `renderEventPopover`) — in that shape, call `useCapabilities()` once at the top of the real component instead and re-derive the own/others branch manually per item (see `meetings-calendar.tsx`'s own comment for the worked example). Whenever a frontend module's hand-written TypeScript type (`types.ts`) mirrors a backend row shape, keep it in sync with new ownership columns — several were missing `createdByUserId` even after the backend had carried it for multiple phases, caught only when wiring the UI.
- **Deferred to v2, do not build**: multi-org (one owner account managing several separate organisations/instances) and cross-owner content ownership (restricting one Owner's access to another Owner's created records). See PRD §4.2 for why these are deferred and what would need to change to revisit them.
- **Invitation acceptance**: `POST /org/invitations` sends a real email (`sendInvitationEmail` wired in `auth.ts`, reusing `EmailService`) linking to `apps/web/src/app/accept-invite/[id]`, which calls Better Auth's own `getInvitation`/`acceptInvitation`/`rejectInvitation` client-side. Both of those **require an authenticated session matching the invited email** — Better Auth won't create an account inline, so an invitee without a session first goes through `/signup?inviteId=...&email=...` (email locked, pre-filled via the unauthenticated `GET /public/invitations/:id`) or `/login?next=/accept-invite/...`. There is still no automatic default-Team assignment on accept (the invited Staff user has zero Team memberships until an Owner assigns one from the Teams page) — if that's added later, it must be real application code run **after** `acceptInvitation` succeeds, **not** a `databaseHooks.member` hook: Better Auth 1.4.21's `databaseHooks` type (`BaseModelNames`) only covers `user`/`account`/`session`/`verification`, and the `organization` plugin's `member`/`invitation` writes aren't exposed through that hook surface (confirmed against `@better-auth/core`'s `type.d.mts` — re-check that type before re-attempting this, in case a future Better Auth upgrade changes it).

## Non-goals for v1 (PRD §1.5) — do not build these

Multi-tenant SaaS hosting (including one owner account managing multiple organisations — see the permission model section above), payroll/HR/attendance, inventory with stock valuation, marketing automation, country-specific statutory filing, customer self-service accounts, multi-currency, bank feed auto-import, native desktop app. If a task seems to require one of these, stop and confirm scope with the user rather than proceeding.

- Unit tests are mandatory for money, tax, and posting-rule modules — this is where silent financial bugs hide.
- Integration tests per document lifecycle (quote, invoice, payment, etc.).

Extend `apps/e2e/tests/` for future coverage rather than starting a second E2E setup.
