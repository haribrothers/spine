# Principles

Rules every component and screen in Spine follows, not just suggestions. Where a component's own doc page repeats one of these, it's because that component is where the rule is actually enforced.

## One primary action per screen

The primary (filled blue) Button variant is reserved for the single most important action on a page — everything else is secondary, ghost, or a plain link. A screen with two primary buttons is a bug, not a design choice: it forces the user to guess which action actually matters.

## Financial status is a reserved palette

Paid, due-soon, overdue, and draft each have exactly one meaning across the entire product, carried by `StatusChip`. They are never repurposed for a generic badge, count, or tag — that's what `Badge` is for. This isn't just a style guideline: `StatusChip`'s `status` prop only accepts those four values at the type level, so a screen can't accidentally borrow "overdue red" to mean something else.

Color is never the sole carrier of that meaning either — every `StatusChip` renders a text label alongside its color, so status reads correctly for colorblind users and in grayscale print (a printed invoice, a black-and-white photocopy of a job sheet).

## Every token is overridable

A self-hoster reskins Spine by overriding the CSS custom properties in `packages/config/tailwind-preset.css` — never by editing component source. No component hardcodes a hex color, a pixel radius, or a spacing value; everything traces back to a token. This is what makes a preset swap (§S-10.4/S-10.5 of the PRD) a real, supportable customization path instead of an unofficial fork.

## 44px touch targets on mobile

Any control used in the field-companion app (`apps/mobile`) meets the 44×44px minimum touch target, since field users are frequently one-handed or wearing gloves on a job site. `Button`'s `touch` size exists specifically for this; most other interactive components (`Checkbox`, `RadioGroup`, `Switch`) already meet it via padding even at their default visual size.

## Borders and tonal steps, not shadows, for structure

Depth is conveyed through borders and a single tonal step (`surface` vs. `background`), not drop shadows — a card is a bordered surface, not a floating shadowed box. Shadows are reserved for genuinely temporary, layered UI: `Dialog`, `Drawer`, `Popover`, `Toast`. Anything else — a `Card`, a `Table`, a page section — uses a border.

## Never a blank screen with no next action

Every zero-results list, first-run dashboard, and empty state uses `EmptyState` — icon, message, and a primary action — rather than a bare blank area. This is Spine's onboarding principle from PRD §FEAT-12 applied everywhere, not just during first-run setup: an owner should never open a screen and see nothing with no indication of what to do next.

## Motion confirms, it doesn't decorate

Motion in Spine exists to confirm a state changed — a toast arriving, a modal opening, a row expanding — never to delight or draw attention to itself. Every transition uses one of four durations (`instant`, `fast`, `base`, `slow`) from the token set, and respects `prefers-reduced-motion`.
